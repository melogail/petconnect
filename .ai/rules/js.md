## Extract Vue components early, keep pages simple
Pages in `resources/js/pages/` compose components; they do not hold markup blocks or logic that could live in a component.

- Reuse `resources/js/components/ui/**` before writing anything new; extract a shared component the moment a block of markup appears twice or a page grows past roughly 150 lines.
- One component, one job. Props in, events out — no cross-component state juggling.
- Prefer the simplest thing that works: `<Form>` / `useForm` over hand-rolled submit handlers, Wayfinder route helpers from `@/actions` and `@/routes` over hardcoded URLs.

## An empty array or object never reaches the server on a form that uploads a file
Inertia serialises to FormData as soon as the payload contains a File, and `objectToFormData` appends nothing at all for `[]` or `{}`. `null` survives (it is appended as `''`, then ConvertEmptyStringsToNull turns it back into null). So on any form with a file input, an empty repeater, an empty tag list or an empty coordinate object arrives as a missing key, not as an empty one.

Two obligations follow. Send `null`, not `[]` or `{}`, when the intent is "explicitly cleared" and the backend distinguishes the two. And do not assume a backend `present` rule can be satisfied by an empty collection — it cannot; the backend rules deliberately omit `present` on collection keys for this reason (see .ai/rules/requests.md).

The pet create form is the live case: it always posts a required `featuredImage`, so it is always multipart, and a listing with no traits/vaccinations/medications/allergies/extras/map pin sends six fewer keys than the same listing edited without a new photo.

## Regenerating Wayfinder by hand needs --with-form, or it silently drops the form variants
`vite.config.ts` configures `wayfinder({ formVariants: true })`, so the build emits a `.form` helper next to every route/action function. A bare `php artisan wayfinder:generate` does **not** read `vite.config.ts` — form variants are opt-in per invocation — so it overwrites `resources/js/{actions,routes}/**` with a tree that has no `.form` on anything.

Nothing fails at generation time. It surfaces later and somewhere else: `npm run types:check` reports `TS2339: Property 'form' does not exist` at every existing `v-bind="store.form()"` call site (15 of them, all pre-existing scaffold pages such as `resources/js/pages/auth/Login.vue`), which reads like the *pages* are broken. They are not; the generated tree is.

Regenerate with `php artisan wayfinder:generate --with-form --no-interaction`, or just run `npm run build` and let the vite plugin do it with the configured options. Then confirm with `npm run types:check`.

`resources/js/{actions,routes,wayfinder}/**` is generated output: regenerate it, never hand-edit it, and never "fix" a `.form` error by changing the `.vue` call site.

## Browser verification: the recipe, the instruments, and their limits
Everything in this section is **frontend instrumentation** and lives here, in the file globbed `resources/js/**`, because that is who reaches for it. The *argument* that produced it — a false "not observable by this fleet" inference hardened into a standing prohibition, and the boundary statement it ends in — is review-time and stays in `.ai/rules/general.md`, "Amplification toward inaction: absence of a tool is evidence about the tool, not about the task". Read that one before you write "cannot be checked" into a brief; read this one when you need a number off a render.

Symptom that sends you here: a claim about rendered behaviour you can only support with *"reasoned, not observed"* — or a page that loads and then fails with wrong or missing modules rather than a manifest error.

**The method, recorded so nobody re-derives it. Browser verification needs no new dependency and touches no repo file.**

1. `rsync` the working tree to an isolated copy **outside the repo**.
2. Symlink `vendor` and `node_modules` into the copy.
3. **Remove `public/hot` in the copy** — see the `public/hot` trap in `.ai/rules/general.md`, "Amplification toward inaction"; skipping this step is what costs the debugging cycle. The symptom does not name its cause: the page loads and then fails with **wrong or missing modules, not a manifest error**.
4. `npm run build` **in the copy, never against the working tree** — a build against the tree rewrites shared, gitignored `public/build/` underneath whatever else is running, which is the same concurrent-writer hazard `.ai/rules/general.md`, "Run Pint with explicit paths", records.
5. Serve the copy with `php artisan serve` against a **throwaway sqlite database**, with explicit `DB_CONNECTION=`/`DB_DATABASE=` shell overrides rather than an `--env` flag (`.ai/rules/migrations.md` records why the flag is the wrong instrument for anything destructive).
6. Drive Chrome over CDP.

Net effect: no dependency added, no repo file changed, only gitignored `public/build/` regenerated inside the copy.

**Working limits of the instruments, each observed in one Chrome build on one machine — treat them as observations to retry, not as general claims about CDP.** The hedge is not decorative: the first entry below has already been half-retired by a retry, and it says which half.

- **Synthetic input — half of this limit is gone, and the correction is exactly half.** It read *"Synthetic input did not reach the page in that build"*, flat, and that is now too strong. Retried and measured 2026-09-06 on **Chrome 152**: trusted **`Input.dispatchKeyEvent` works** — a dispatched Tab reached the notification badge with `:focus-visible` matching, and a dispatched ArrowDown scrolled a focused region from `scrollTop` 0 to 240. What did **not** change: **clicks still required in-page `PointerEvent`/`click` dispatch** on the target element, and **`Input.dispatchMouseEvent` was not retried at all**, so its status is **unknown, not working**. *Retried once, later the same day, Chrome 152 headless against the real host:* a single `mouseMoved` to the centre of a feed card produced **no `:hover` state** in the next screenshot — the card's `group-hover` icon bar stayed at opacity 0 — while a programmatic `el.focus()` on one of the bar's icons took the same bar to opacity 1 through `group-focus-within`. One attempt, one event type; read it as "a lone `mouseMoved` did not hover", not as "mouse dispatch does not work", and for hover-revealed UI focus the control instead. Do not round this off to "synthetic input works now" — keyboard yes, mouse unretried, in-page dispatch still the working path for clicks. Reversing the whole claim would overshoot as far in the other direction as the flat version did in this one.
- **A programmatic `el.focus()` is not a substitute for a trusted Tab, and anyone who treats it as one draws a wrong conclusion.** Measured in the same run: `el.focus()` on the badge did **not** open its tooltip, where a dispatched Tab did. That is what reka-ui's `ignoreNonKeyboardFocus` plus `:focus-visible` predicts — neither matches a focus that arrived programmatically. The failure is silent and points the wrong way: a re-checker who uses `.focus()` sees nothing open and concludes the badge's focusability buys nothing, when what they measured is the instrument. Anything whose behaviour is keyed on *how* focus arrived gets `Input.dispatchKeyEvent`, per the recipe above.
- **reka-ui `Select`s could not be driven that way at all** (`reka-ui ^2.9.8`, `package.json:25`, wrapped under `resources/js/components/ui/select/`). Form values were set on the **hidden native `<select>` element the reka Select renders and that `<Form>` (`@inertiajs/vue3 ^3.0.0`) serialises** — set `.value` there, dispatch `change`, submit.

**That correction is the hedge doing its job, and it is kept beside the limit rather than in a footnote.** The limit was deliberately written as *an observation from one Chrome build on one machine, to retry rather than a general claim about CDP*. The retry happened, and it moved the limit — which is the outcome the hedge was for. An unhedged *"synthetic input does not work"* is precisely the sentence that would have stopped the retry, which is what makes the hedge load-bearing rather than decorative. **Partly** is the word to keep: the mouse half is unretried, not impossible, and it keeps the hedge until somebody retries it. That this is the **fourth** such dissolution in one session is counted in `.ai/rules/general.md`, "Amplification toward inaction" — the argument lives there, this is the instrument.

Symptom vocabulary: a `[data-sidebar]` element, a `SidebarProvider` import, `page.props.sidebarOpen`, a `dashboard` route helper, or a `breadcrumbs` attribute rendered on a page's root element — any of these means somebody re-scaffolded.

## `app.ts` module-level code runs on the SSR server for every request — a scheduler-fired `document` read kills the dev server on the second render
There is no `resources/js/ssr.ts`; `@inertiajs/vite` builds the server entry from `app.ts` itself, so every top-level statement in `app.ts` and its import graph — `initializeTheme()`, `initializeFlashToast()`, `initializeLocaleDirection()` — executes **once per SSR process**, and `usePage()` there is a module-level ref shared by every request that process renders. A watcher registered at module level therefore re-fires on the **second** request's page assignment, from Vue's scheduler (`flushJobs`), outside the render's `try`. An uncaught throw there exits Node, and in development Node is the Vite dev server.

Symptom strings, because this is what you see before you know the cause: `ERR_CONNECTION_RESET` / `ERR_CONNECTION_REFUSED` for `http://127.0.0.1:5173/@vite/client` and every module after the first page of a session; a `vite` process whose age resets to seconds every minute under `php artisan dev`; a page that loads once and then paints blank. In the dev server's own output: `ReferenceError: document is not defined … at flushJobs … Node.js v22`. PHP never sees any of it — `HttpGateway::dispatch` catches the connection failure and falls back to client rendering, so the response is a 200 with no SSR body and the crash is invisible from the Laravel side.

Rule: anything reachable from `app.ts` at module level guards on `typeof document === 'undefined'` (or `window`) **before registering a watcher**, not only inside the callback — the registration is what puts the callback on the server's scheduler. `useGeolocation.ts` already does this for storage; `localeDirection.ts` now does it for the watcher (its docblock has the measurement).

Instrument, so nobody argues from a build again: capture a page object (`<script data-page="app" type="application/json">` in any rendered document, or `X-Inertia: true` with the current `X-Inertia-Version`), then `curl --data-binary @page.json http://127.0.0.1:<port>/__inertia_ssr` **twice, two different components**, and check the port still listens. `npm run build:ssr` exiting 0 proves the bundle compiles; it renders nothing.
