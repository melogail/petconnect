## Resolved: the branded, locale-aware VerifyEmailNotification is ported
This used to record a deferral. Phase 2e landed the whole chain it was waiting on — `resources/views/emails/verify-email.blade.php`, `lang/en` + `lang/ar` + the two JSON catalogues, and the locale mechanism (`SetLocale`, `Actions\Profiles\ApplyUserLocale`, `HasLocalePreference`) — so `User::sendEmailVerificationNotification()` now sends `App\Notifications\VerifyEmailNotification`.

It extends `Illuminate\Auth\Notifications\VerifyEmail` and overrides `toMail()` only. Do not reimplement `verificationUrl()`: it builds the signed, expiring route from `auth.verification.expire` and honours `VerifyEmail::createUrlUsing()`, all of which is security-relevant framework behaviour.

Locale comes from the **notifiable** (`preferredLocale()`), never from `App::getLocale()` — the mail may render long after and elsewhere than the request that triggered it — and every string is translated with the explicit third `$locale` argument rather than by switching the application locale and switching it back. Direction comes from `petconnect.locales.rtl`, so a new RTL language is a config entry.

**`tests/Feature/Auth/VerificationNotificationTest` asserts `VerifyEmailNotification::class` and is green.** It used to assert `VerifyEmail::class` and failed, because `NotificationFake` keys sent notifications by exact class name rather than by `instanceof`, so the subclass did not satisfy it; the tester changed the assertion in the same phase. Keep the exact-class trap in mind for any notification that is subclassed — the fake will not match the parent.

## Notification payloads store translation keys, never rendered text
A database notification row outlives the reader's locale, so never call `__()` when building `toArray()`. Store `message_key` plus `message_replace` and let the client render; a user who switches language must see their whole history in the new language, not text frozen at write time.

That reason is the whole reason, and it stands on its own. This paragraph used to add a second one — "`lang/` contains only `lang/vendor/nova`, so `__('notifications.liked_pet')` returns the key and the literal string gets persisted" — which Phase 2e made false and, editing this very file, failed to correct. `lang/` now holds `en/`, `ar/`, `en.json` and `ar.json`, and `notifications.liked_pet` resolves in both. Do not repeat the missing-catalogue argument.

Nothing changes about the rule. A row written today is read months later by someone who has since switched language, so rendering at write time is wrong even when the catalogue is complete — which is exactly why it must not rest on a fact about `lang/` that a later phase can flip. The same applies to any "someone"-style fallback: emit `null` and let the client supply its own localized default.
