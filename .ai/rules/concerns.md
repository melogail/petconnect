# Concerns

> **`.ai/rules/app.md` also applies to this path and must be read too.** Its `app/**` glob
> covers everything covered here; this file adds to it rather than replacing it. Do not stop at
> the first row of the index that matches — the index is regenerated by `record-rule` on every
> write, so its ordering and wording carry no meaning.

> **Loosening a rule can lose a capability the same way deleting one does** — and the validation
> rules live in this directory (`PetValidationRules`, `ProfileValidationRules`), not in the Form
> Requests, so a `required` relaxed to `nullable` or `sometimes` is typed here. The review check,
> its operationalisation and the measured instance live in `.ai/rules/general.md`, "Review what a
> change REMOVED — and what it merely made optional". This is a pointer, not a copy.

## Traits live in app/Concerns, not app/Traits
This project has no app/Traits directory; `php artisan make:trait` writes to app/Concerns and the starter kit already used it (PasswordValidationRules). Model behaviour traits ported from the legacy app/Traits live here: HasComments, HasLikes, HasSaves, HasReviews, HasReport. The legacy HasPipeline was dropped — use real pipelines per .ai/rules/pipelines.md.

## A form's read resource and its rules must use identical key names
When an API Resource is the read side of a form, every key it emits under a group the form posts back must have a validation rule of exactly that name. Prefer camelCase for nested form groups. Rename both sides in the same change, and keep the pipeline's `data_get()` paths in step.

They drifted once already: PetDetailResource emitted `health.spayed_neutered`, `location.postal_code`, `additional_info` while PetValidationRules only accepted the camelCase spellings. Nothing failed loudly — `validated()` drops an unmatched key, and the update flow writes a complete attribute bag, so price, breed, vaccinations, traits, vet_name, address and lat were written as null on save and `spayed_neutered` flipped to false via `(bool) null`.

The rules for the pet form live in the `App\Concerns\PetValidationRules` trait, not in the requests themselves, so the person most likely to break parity is renaming a key in a Concern. Guard: every **scalar** key the write bag owns carries `present` alongside `nullable`, so an absent key is a 422 rather than a silent wipe — a renamed scalar rule that no longer matches the resource fails loudly.

**Collection keys cannot carry that guard** — a multipart request cannot express an empty array, so `present` there would 422 every create with an empty repeater (see "Never put `present` on a collection key" in .ai/rules/requests.md). Renaming `traits`, `additionalInfo`, `health.vaccinations`, `health.medications`, `health.allergies` or `location.coordinates` therefore still wipes silently, and the resource↔Form-Request key-parity test is the only thing that catches it. Same for renaming *both* `location.coordinates.lat` and `.lng` at once: `required_with` only fires when one of the pair survives.

(Kept in sync with the copies in the other files: the trap bites whoever edits the resource, the request, or the concern that holds the rules. .ai/rules/resources.md, .ai/rules/requests.md and .ai/rules/concerns.md carry the same text. Edit all three together.)

## `sometimes` gates the whole attribute, implicit rules included — do not pair it with `required_with`
`Validator::isValidatable()` calls `passesOptionalCheck()`, which returns false the moment an attribute carrying `sometimes` is absent from the payload. That skips **every** rule on that attribute, including implicit ones like `required_with` and `required_without`. So `['sometimes', 'nullable', 'current_password', 'required_with:password']` never fires `required_with` for the case it exists to catch — the key being missing.

Measured on `ProfileValidationRules::passwordChangeRules()`: sending `password` with `current_password` omitted passed validation outright, and the only thing stopping the change was `UpdateProfile\VerifyCurrentPassword` throwing `IncorrectCurrentPassword` — so the user was told "The password is incorrect." when they had supplied no proof at all. Reordering the rules does not help and was measured not to; the gate sits ahead of the rule list.

Fix: drop `sometimes` and let `nullable` carry the optionality. `validated()` still omits absent keys either way (it includes only keys present in the data), so PATCH semantics are unaffected. Order `required_with` before the rule that inspects the value, so the missing-field message wins when both could fire.

## `sometimes` swept out of every cross-field rule; the pair rules are `nullable` only
Third and last instance of the `sometimes` trap is fixed: ProfileValidationRules::latitudeRules()/longitudeRules() were `sometimes|nullable|numeric|between|required_with:...`, which meant `required_with` could only fire when both keys were already on the wire. Measured before the fix: `PUT /nova-api/users/{id}` and `PATCH settings/profile` with `lat` alone both succeeded and wrote `lat = 51.5, lng = null`. Both are now `['nullable', 'required_with:<other>', 'numeric', 'between:...']` and both entry points 422 on `lng`.

Full sweep of every `sometimes` in app/ (there are only two files): ProfileValidationRules phone/bio/addressLine/timezone/username/locale/avatar carry only value rules (string, max, timezone, alpha_dash, unique, Rule::in, image/mimes) — none cross-field or presence-based, all safe and correctly `sometimes|nullable` for PATCH semantics. MessageValidationRules::messageTypeRules() is `['sometimes', Rule::enum]` — a value rule, safe. Nothing else in app/ uses `sometimes`.

Standing rule for new code: `sometimes` may never sit on an attribute that also carries `required_with`, `required_without`, `required_if`, `confirmed`, `same`, `different`, `after`, `before`, `gte` or `lte`. Use `nullable` for the optionality, or compute the presence rule from `$this->filled()` the way ListHomeFeedRequest does for latitude/longitude. `validated()` omits absent keys either way — it decides on a `$missingValue` sentinel from `data_get()` and never consults `sometimes` — so dropping it never changes PATCH semantics.

(Mirrored into .ai/rules/requests.md, because the rules that carry this trap live in `App\Concerns\*ValidationRules` but the person who reintroduces it is editing a Form Request. Edit both copies together. Not mirrored into .ai/rules/resources.md: a read resource has no validation rules for it to bite.)

## Both photo ceilings live on PetPhotoRules, so a controller can ship them
`maxGalleryImages()` moved from `PetValidationRules` down to `PetPhotoRules`, beside `maxImageKilobytes()`, and `PetPhotoRules::photoBounds()` is built from the two. `Web\PetController::create` and `::edit` ship it as the `photoBounds` prop — the fourth of these, after `reviewBounds`, `commentBounds` and `messageBounds`, and the last hardcoded config mirror on the client (`pets/Create.vue` and `pets/Edit.vue` carried 3 and 512 by hand).

It is `PetPhotoRules` and not `PetValidationRules` because a controller cannot take the latter: it carries `featuredImage()` / `galleryImages()`, which call `Illuminate\Http\Request::file()` and would fatal off a Form Request, and rule methods that read `$this->input()`. `PetPhotoRules` is the half that is safe anywhere — `App\Nova\Pet` already uses it for that reason, and now gains `photoBounds()` too. `PetValidationRules` still `use`s it, so the `max:` rules are unchanged and cannot disagree with the prop.

Rule for the next one: a bound the client has to render goes in an accessor on the trait the `max:`/`min:` rule is built from, never a second `config()` call in the controller.

## A client that pages a list must be shipped the page size — it cannot infer it
`petconnect.pets.detail_comment_page_size` (the slice `LoadPetDetail` ships inside `pets.show`) and `petconnect.comments.thread_per_page` (what `comments.index` pages by) are independent env vars. CommentThread.vue assumed they matched, so its first "load more" asked for page 1 — the slice already on screen — deduped to nothing, and the user had to click twice.

Fix, and the shape for the next one: the page size goes on the bounds prop, read through the same accessor the paginator uses. `CommentValidationRules::threadPerPage()` now backs both `commentBounds.thread_per_page` and `ListCommentThread`'s default `$perPage`, so there is one spelling of the key. A paging size on a `*ValidationRules` trait is deliberate — it is not a rule, but that trait is where the config key lives, and `Actions\Fortify\CreateNewUser` already sets the precedent of an Action taking one. Nothing on it touches a Request, so it is safe off a Form Request.

The cursor also needs a total counted in the same units as the thing being paged. `pets.show` ships `pet.root_comments_count` (`withCount('rootComments')`, folded into the existing `withCount`, so no extra query) beside `comments_count`: the latter is the whole morphMany, replies included, and comparing shipped roots against it is what lit the button up wrongly in the first place.
