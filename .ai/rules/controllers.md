## Authorization is $this->authorize() in the controller — never in a Form Request
App\Http\Controllers\Controller uses AuthorizesRequests. **Every action that acts on a policy-governed model calls `$this->authorize()`** against that model's policy — including the public ones, where the policy method takes `?User` and returns true (PetPolicy::viewAny for the home feed, PetPolicy::view for a listing page). A guest-visible page should be a recorded decision in a policy, not the absence of a check.

Actions with no policy-governed model do not call it. The Settings controllers act on the authenticated user, which route middleware already establishes, and there is no second party whose access is in question; adding a policy there would be ceremony. That is the only exemption — if an action loads, writes or exposes a model somebody else could own, it authorizes.

Form Requests validate only; do not implement authorize() in them, and do not use Gate::authorize() in controllers.

Why: the legacy app split the same decision three ways — StorePetRequest::authorize() returned true while its controller never called the policy (anyone could publish), UpdatePetRequest checked the policy itself, and PetController::edit checked nothing at all (any verified account could read another owner's vet details, exact coordinates and medications). One convention, one place to audit.

## A GET action never writes: Inertia v3 prefetching makes it a bug, not a purity argument
The legacy ConversationController::show called markAsRead inside the GET, so rendering the page mutated state. Under Inertia v3 that is not just non-idempotent: link prefetching and instant visits issue real GET requests on hover and on intent, so a hovered inbox row would mark a thread read that nobody opened and the unread badge would clear itself as the pointer crossed the list. Browsers and proxies may also repeat a GET.

`conversations.show` is therefore a pure read and the read cursor moves on POST `conversations.read`, which the thread page fires after it renders; `unread` is on the inbox payload so the client can skip the POST for threads already read. Cost is one extra request per thread opened.

Rule: if a GET action needs to record that something was seen, split the write onto its own POST route. RecordPetView is the exception that proves it — it is deduped per visitor per window precisely because it sits on a GET.

## back() from a write costs a whole document when the caller is not an Inertia visit — known finding on notifications.read
**Recorded as a known finding awaiting a decision, not as outstanding work, and it blocks no gate.** It is pre-existing at HEAD `2ed96da`: `git diff 2ed96da -- app/Http/Controllers/Web/NotificationController.php` is empty, so nothing in the current phase introduced or worsened it. It is here so the next agent inherits the analysis instead of rediscovering it from the `SyntaxError`.

The shape. `NotificationController::markAsRead` answers `back()`, like every write in that controller. The client fires it with Inertia v3's `useHttp` rather than a `router` visit, deliberately — it runs as the reader follows the notification's deep link, and a visit would be cancelled by that navigation, leaving the row unread (`resources/js/composables/useNotificationInbox.ts:123-135`, read 2026-09-06; re-grep, do not trust the number). A `useHttp` request carries no `X-Inertia` header, so the 302 is followed as a plain XHR GET and the server renders the **whole blade document** for whatever page the reader is on — and a full document is exactly what re-sends the `Inertia::once` translation catalogue, **+29,535 B (en) / +81,662 B (ar) uncompressed, ~8.5/12.3 KB gzipped** (`.ai/rules/lang.md:25`; that figure was measured on a full visit, and this round trip inherits it because it *is* a full document load — it has not been measured on this endpoint). `useHttp` then runs `JSON.parse` over that HTML, so a **successful** mark-read rejects with a `SyntaxError` that the client's catch has to tell apart from a real failure. Every row click therefore buys a second request, a full page render, the catalogue, and a parse failure used as a success signal.

The candidate fix, so it is not re-derived: answer **`204 No Content`** when the caller is not an Inertia visit, keeping `back()` for the visit case — one branch that removes the render, the catalogue bytes and the `SyntaxError` discrimination together. Not done, because it changes the response contract of an endpoint the client is currently written against and the client's catch wants to change in the same commit: one decision, two owners, so it is not a drive-by. If you pick it up, measure the round trip first (response bytes and query count for one `notifications.read`) rather than arguing from the numbers above — see "Measure before arguing" in `.ai/rules/general.md`.

Read it alongside "A GET action never writes" above: that section settles *which verb* a read-marking write takes, this one is about *what the write answers*, and the two are independent.
