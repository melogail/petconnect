# Requests

> the first row of the index that matches — the index is regenerated by `record-rule` on every

## A form's read resource and its rules must use identical key names
When an API Resource is the read side of a form, every key it emits under a group the form posts back must have a validation rule of exactly that name. Prefer camelCase for nested form groups. Rename both sides in the same change, and keep the pipeline's `data_get()` paths in step.

They drifted once already: PetDetailResource emitted `health.spayed_neutered`, `location.postal_code`, `additional_info` while PetValidationRules only accepted the camelCase spellings. Nothing failed loudly — `validated()` drops an unmatched key, and the update flow writes a complete attribute bag, so price, breed, vaccinations, traits, vet_name, address and lat were written as null on save and `spayed_neutered` flipped to false via `(bool) null`.

The rules for the pet form live in the `App\Concerns\PetValidationRules` trait, not in the requests themselves, so the person most likely to break parity is renaming a key in a Concern. Guard: every **scalar** key the write bag owns carries `present` alongside `nullable`, so an absent key is a 422 rather than a silent wipe — a renamed scalar rule that no longer matches the resource fails loudly.

**Collection keys cannot carry that guard** — a multipart request cannot express an empty array, so `present` there would 422 every create with an empty repeater (see "Never put `present` on a collection key" in .ai/rules/requests.md). Renaming `traits`, `additionalInfo`, `health.vaccinations`, `health.medications`, `health.allergies` or `location.coordinates` therefore still wipes silently, and the resource↔Form-Request key-parity test is the only thing that catches it. Same for renaming *both* `location.coordinates.lat` and `.lng` at once: `required_with` only fires when one of the pair survives.

(Kept in sync with the copies in the other files: the trap bites whoever edits the resource, the request, or the concern that holds the rules. .ai/rules/resources.md, .ai/rules/requests.md and .ai/rules/concerns.md carry the same text. Edit all three together.)

## Never put `present` on a collection key: multipart cannot express an empty array
Inertia's FormData serialiser (`objectToFormData` in @inertiajs/core) appends NOTHING for an empty array or empty object, while `null` is appended as `''` and comes back as null through ConvertEmptyStringsToNull. Any request that carries a File is multipart, so on those requests an empty collection is indistinguishable from an absent key.

Rule: `present` goes on a scalar key, or on a group whose leaves are themselves all `present` (which keeps the group serialised). It never goes on a variable-length collection or an optional group. In PetValidationRules that means `traits`, `additionalInfo`, `health.vaccinations`, `health.medications`, `health.allergies` and `location.coordinates` carry no `present`, while `health` keeps it because its twelve scalar leaves are always on the wire.

No feature test can catch a violation: Laravel's test client hands PHP arrays to the request whatever transport is declared, so `->post(..., ['traits' => []])` passes a `present` rule that a real browser would 422. Reason it through from the payload the frontend actually builds.

Cost of the exemption: renaming a collection key silently wipes it instead of 422ing. The resource↔Form-Request key-parity test is the guard for that.
