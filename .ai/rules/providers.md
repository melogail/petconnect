## Enforce a morph map before any data is seeded
The morph map lives in `AppServiceProvider::configureMorphMap()` via `Relation::enforceMorphMap([...])`, called from `boot()`. Register every morphable model there before any data is seeded, and keep it updated as polymorphic models are added.

Five polymorphic relations (`likes`, `saves`, `comments`, `reviews`, `reports`) plus `media.model_type` and `notifications.notifiable_type` store these aliases. The legacy app stored fully-qualified class names and called `enforceMorphMap()` nowhere, so any namespace or class rename orphaned every polymorphic row. Fixing it after seeding means a data migration, so the map has to land first. `App\MediaLibrary\MediaPathGenerator` also builds stored file paths out of `media.model_type`, so an alias here is effectively permanent once files exist.

(Kept in sync with the copy in the other file: the trap bites both the model author and the person editing AppServiceProvider, so .ai/rules/models.md and .ai/rules/providers.md carry the same text. Edit both together.)

## Every Nova resource model must be in the morph map (ActionEvent)
Nova's `ActionEvent` writes `actionable_type`, `target_type` and `model_type` as morph values. Because `Relation::enforceMorphMap()` is enforced in `AppServiceProvider::boot()`, any model exposed as a Nova resource that is missing from the map throws `ClassMorphViolationException` at runtime the moment a Nova action runs against it. When you add a Nova resource, add its model to `configureMorphMap()` in the same change — not just the models used in the app's own polymorphic relations.

(Kept in sync with the copy in the other file: .ai/rules/models.md and .ai/rules/providers.md carry the same text. Edit both together.)

## The Nova scope-out for lazy loading is Util::isNovaRequest(), not a path prefix
`configureLazyLoadingViolations()` replaces `Model::handleLazyLoadingViolation()` wholesale, so it must do two things the framework did for free:

- Restore the early return for a model that is `! $exists` or `wasRecentlyCreated`. Dropping it is a silent divergence from framework behaviour.
- Decide "is this Nova?" with `Laravel\Nova\Util::isNovaRequest($request)`. Nova registers 110 routes: 32 under `nova/`, **76 under `nova-api/*`** (every resource index, detail, relatable and action field resolution — the code that actually lazy loads) and 2 under `nova-vendor/*`, of which 3 routes in total are unnamed. The previous `$request->is(config('nova.path'), ...)` matched only the SPA shell and returned false for all 78 of the rest, so the exemption looked verified (`/nova` renders fine) while covering nothing that resolves a field. `$request->routeIs('nova.*')` covers 107 of the 110 but misses the unnamed `nova-vendor/ebess/advanced-nova-media-library/*` media routes; Nova's own helper covers all of them plus the `nova.domain` install and tracks the package.

The exemption is per request rather than a global switch on purpose: the guardrail is worth more on the verticals still to be built than a green Nova is worth losing it.

## runningInConsole() is not "there is no request" — the test suite is console too
`AppServiceProvider::isNovaRequest()` guarded on `runningInConsole()` alone. That is `PHP_SAPI === 'cli'`, which is true for every Pest test *including a simulated HTTP request*, so the Nova lazy-loading exemption was dead in the one place it needed proving: `GET /nova-api/{users,pets,categories,breeds}` 500'd with LazyLoadingViolationException under test while working live. It was masked because `Builder::hydrate()` only arms the guard above 1 row and every Nova fixture seeded one.

The guard is now `runningInConsole() && ! runningUnitTests()`, then `Util::isNovaRequest($request)`. An artisan command, queue worker or scheduler tick is console-and-not-a-test and takes the early return (its `request` is the placeholder `SetRequestForConsole` builds from `config('app.url')`); a test is console-and-a-test and gets the real question asked against the request the kernel bound. Verified in the test environment: `isNovaRequest()` is true for `/nova-api/users` and false for `/pets`.

Anywhere else you reach for `runningInConsole()` to mean "no HTTP request exists", it will be wrong under test in the same way.

## Throttling a route Fortify or Nova registers: ThrottleAuthRoutes in the package's middleware config
`config('fortify.limiters')` has three slots (login, two-factor, passkeys) and Nova reads those plus `verification`. There is no slot for `register.store`, `password.email`, `password.confirm.store` or `nova.password.confirm` — all four shipped unthrottled, and the first three were measured as an open password oracle / mail relay in the Phase 6 audit.

`App\Http\Middleware\ThrottleAuthRoutes` holds a route-name => limiter-name map and delegates to `Illuminate\Routing\Middleware\ThrottleRequests` (called with exactly 3 args, which is what selects its named-limiter path). It is attached in `config/fortify.php` `middleware` and `config/nova.php` `api_middleware` — the only say the application has over middleware on routes a package declares — and no-ops for every other route name. Add an entry there for the next such route; do not invent a second mechanism.

The three alternatives are all traps and were each tried: redeclaring the route in routes/web.php loses, because `RouteServiceProvider` loads the app's routes from an `$app->booted()` callback and both packages register in `boot()` (Fortify's four sit at positions 4-18 of the collection). Mutating the Route objects from a `booted()` callback silently does nothing under `route:cache`, because `loadCachedRoutes()` queues the require of the cache file as a *later* booted callback. `Fortify::$registersRoutes = false` means owning a copy of the package's routes file.

New limiters live in `AppServiceProvider::configureRateLimiters()` like every other one. `password-confirmations` keys on `user id|ip` via `passwordConfirmationKey()` (not the usual `rateLimitKey()`), and has to ask both the default guard and `config('nova.guard')` because Fortify's copy of the route is `web` and Nova's is `admin`.

## Correction: ThrottleAuthRoutes attaches from config('nova.middleware'), not api_middleware
The section above says the Nova half of ThrottleAuthRoutes lives in `config('nova.api_middleware')`. That is no longer true and was never sufficient. NovaCoreServiceProvider builds three groups: `nova` from `config('nova.middleware')`, `nova:api` from `config('nova.api_middleware')` (whose first entry is `nova`), and `nova:auth` from `config('nova.middleware')` plus RedirectIfAuthenticated. Nova registers its login and password-reset routes with `nova:auth`, which `api_middleware` never reaches — so `nova.password.reset` (POST nova/password/reset, an unmetered Hash::check per unexpired token row that pays out an *admin* password on a hit) could not be throttled from there. The middleware now sits in `config('nova.middleware')`, which reaches all three groups once; listing it in both would be redundant rather than harmful, since Router::uniqueMiddleware() collapses the duplicate. Verify an attachment with `$router->gatherRouteMiddleware($route)`, not `route:list -v` — route:list prints `nova` / `nova:auth` unexpanded and shows nothing.

Also: the LIMITERS map keys on route *names*, and handle() returns early on a null name, so an entry for an unnamed route is dead code that fails silently. 3 of Nova's 110 routes are unnamed (nova-vendor/ebess/advanced-nova-media-library/*).

Current map: password.confirm.store, nova.password.confirm, register.store, password.email, password.update, nova.password.reset. `password-resets` (5/min, 20/hour) keys on the caller's IP alone via passwordResetKey(): both routes are `guest`, and the submitted email is deliberately excluded because it is attacker-chosen (a fresh bucket per typed address would leave the CPU unbounded) and because an email-keyed bucket lets a stranger lock a victim out of their own recovery.

## Correction: what a failed password-reset submit actually costs (and the token shape)
The `password-resets` rationale used to claim a failing POST buys "a Hash::check per unexpired password_reset_tokens row plus a full Password::defaults() validation, uncompromised() included, an outbound HTTP call". Both halves are false; verified against the framework.

- `DatabaseTokenRepository::exists()` does one `where('email', ...)->first()` and one `hasher->check()`. `email` is the primary key of both `password_reset_tokens` and `admin_password_reset_tokens`, so it is one row per address, never a scan — and the `$record && ! expired && check` chain short-circuits, so a missing or expired row costs zero bcrypt.
- Fortify's `NewPasswordController::store()` validates only `token|email|password` as `required`. `Password::defaults()` runs inside `ResetUserPassword::reset()`, which `PasswordBroker::reset()` invokes only after `validateReset()` accepted the token, so an invalid submission never reaches `uncompromised()` and makes no network call. `uncompromised()` is production-only here anyway (`configureDefaults()`). Nova's `NewPasswordController` subclasses Fortify's and calls `parent::store()`, so it inherits all of it.

Real cost of a rejected POST: one indexed users/admins lookup, one primary-key token-row read, at most one bcrypt, no network call. What justifies 5/min + 20/hour is (a) it is the submit half of a credential flow, and Nova's copy sets an **admin** password, and (b) `PasswordBroker::reset()` runs inside a Timebox at `config('auth.timebox_duration')` — unset, so the framework's 200000 microseconds — which a failure does not `returnEarly()` from, so every rejected submission holds a PHP worker for 200 ms.

Also: the token is not "64 random characters". `createNewToken()` is `hash_hmac('sha256', Str::random(40), $hashKey)` — a 64-character **hex** string, stored hashed again, in a row that expires after 60 minutes. Guessing is still hopeless; the description was wrong, not the conclusion.

Ceilings unchanged. Same text lives in `App\Http\Middleware\ThrottleAuthRoutes` and `config/nova.php` — keep all three in step.

## Guest auth routes key through passwordResetKey(), never rateLimitKey()
`.ai/rules/routes.md` says a public unauthenticated write must use an IP-keyed limiter and never `rateLimitKey()`, "which silently degrades to the IP and hides the decision". `registrations` and `password-reset-links` were violating it: `register.store` and `password.email` are registered `guest:config('fortify.guard')` by Fortify, so `rateLimitKey()` produced the IP only as a fallback and nothing would have failed if either route stopped being `guest`.

Both now call `passwordResetKey()` — the same value on the wire for any caller a `guest` route can serve, but the IP becomes a decision rather than a default. `passwordResetKey()` is now the shared key for all four guest routes in the `ThrottleAuthRoutes` map (`registrations`, `password-reset-links`, `password-resets`); its name is historical, its docblock says so.

One edge case, deliberate: an authenticated caller POSTing to a guest route is now counted against their IP rather than their user id, because `ThrottleAuthRoutes` runs from the package middleware group ahead of the route's `guest`, so the hit lands before `RedirectIfAuthenticated`. Neither key lets them past the redirect. No ceiling changed.
