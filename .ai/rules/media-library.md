# Media Library

> **`.ai/rules/app.md` also applies to this path and must be read too.** Its `app/**` glob
> covers everything covered here; this file adds to it rather than replacing it. Do not stop at
> the first row of the index that matches — the index is regenerated by `record-rule` on every
> write, so its ordering and wording carry no meaning.

## MediaPathGenerator: never touch $media->model, never use class_basename
`getPath()` builds `media/{owner directory}/{model_type}/{model_id}/{media_id}/` from the media row's own columns only.

Two reasons, both measured or bitten before: (1) `$media->model` is an unhydrated `MorphTo` — Laravel does not set the inverse for `morphMany` — so touching it costs one query per media item per URL, and `$model->user` costs a second; a listing page with `Pet::with('media')` issued 4 extra queries for 2 photos. (2) `class_basename($model)` would bake the PHP class name into stored paths; `model_type` already holds the stable morph alias, so renaming a model would orphan every file.

The owner segment comes from the `owner_directory` custom property (`MediaPathGenerator::OWNER_DIRECTORY_PROPERTY`), which whatever attaches media MUST set to the owner's `media_directory_name`. The DB lookup in the generator is a fallback only. The generator is bound `scoped` in `AppServiceProvider::register()` so that fallback can memoise per request; do not memoise statically, it would go stale across a refreshed test database.

The trailing media-id segment is deliberate: without it two same-named uploads on one model overwrite each other, which the legacy generator allowed.

## The owner lookup lives in OwnerDirectoryResolver, and the fallback should now never run
Amends the MediaPathGenerator note above. The owner-directory lookup and its memo moved out of the generator into `App\MediaLibrary\OwnerDirectoryResolver`, because two callers need the same answer for opposite reasons: `Observers\MediaOwnerDirectoryObserver` asks once on `creating` so it can stamp the property before the file is written, and the generator asks on every generated URL where it is a fallback. Both `OwnerDirectoryResolver` and `MediaPathGenerator` are bound `scoped` in `AppServiceProvider::register()`, so the memo still lives exactly one request — do not memoise statically.

Consequence: the database fallback is now expected never to run, because the observer stamps `owner_directory` on any row that arrives without it (see .ai/rules/observers.md). "Whatever attaches media MUST set it" is no longer a rule callers can break — but keep setting it in the Actions that already do, since that path costs no query at all.

## The medialibrary temp-directory leak is closed by a container-bound FileManipulator, not a patch
`spatie/laravel-medialibrary` 11.23.5 `Conversions\FileManipulator::performConversions()` creates a temporary directory, copies the original in, and deletes it on the last line with no `try`/`finally`. Both the 0-byte early return (`filesize(...) === 0`) and any throw out of the conversion loop (`CouldNotLoadImage` on a file GD cannot decode) skip the delete and strand a directory under `storage/media-library/temp`.

`App\MediaLibrary\TemporaryDirectoryCleaningFileManipulator` overrides `performConversions()` **and nothing else** — it calls the parent inside a `try` and cleans up in a `finally`. It exists only because the package lacks that `finally`; delete it when upstream adds one. Do not reimplement the conversion loop in it.

It cannot see the parent's `$temporaryDirectory` (local variable, and `Support\TemporaryDirectory::create()` is a hard static call), so it narrows `media-library.temporary_directory_path` to a private subdirectory for the duration of the call and deletes that whole subdirectory in the `finally`. Do NOT "simplify" this to listing the temp root before and after and deleting what is new: in production a concurrent request's live temporary directory is "new" from this call's point of view and would be deleted out from under a running conversion.

Bound in `AppServiceProvider::register()` with `bind()`, deliberately not `scoped` like `MediaPathGenerator` and `OwnerDirectoryResolver` — those two are scoped because they hold a per-request memo, and this one holds no state at all. The bind covers the inline path, `PerformConversionsJob` and `media-library:regenerate`, because the package resolves the manipulator from the container in all three.

Also in this directory: `ConvertibleImageTypes` is the single source of the accepted image formats (the set the GD driver can decode). Every file rule — `PetPhotoRules::photoFileRules()`, `ProfileValidationRules::avatarFileRules()`, `TaxonomyImageRules::taxonomyImageFileRules()` — and every `acceptsMimeTypes()` on a media collection is built from it. A bare `image` rule is wider: it admits `bmp`, `heic` and `heif`, which no conversion can read, so the raw original gets served in place of a crop. `ImageDecodeVerifier` is the only check in the upload path that is not a header sniff; it loads the file through the same `Spatie\Image\Image` driver the conversion uses.
