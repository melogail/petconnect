# Observers

> **`.ai/rules/app.md` also applies to this path and must be read too.** Its `app/**` glob
> covers everything covered here; this file adds to it rather than replacing it. Do not stop at
> the first row of the index that matches — the index is regenerated by `record-rule` on every
> write, so its ordering and wording carry no meaning.

## Three observers hold invariants seeders and factories depend on — never mute model events
UserObserver::creating assigns the opaque `media_directory_name` — `random_int(10 ** 15, 10 ** 18)`, so 16 to 19 digits (the bound is inclusive) — so uploads are never addressable by user id; factories and seeders deliberately leave the column unset. Uniqueness is the DB unique index's guarantee, not the observer's: the observer draws at random and does not check for a collision.
MessageObserver maintains `conversations.last_message_at`: `created` advances it to the new message's created_at but never moves it backwards, so a seeder or factory inserting a backdated message cannot walk the inbox preview back in time; and `deleted` (soft only — it returns early while force deleting), `restored` and `forceDeleted` recompute the cursor from the remaining messages, so it goes null when the last one is gone.
LikeObserver early-returns unless the likeable implements App\Contracts\Likeable, then notifies `likeNotificationRecipients()` minus the liker, so self-likes are silent. ModelLikedNotification is not queued.
Consequence: do not mute model events to speed seeding up (see .ai/rules/seeders.md) and do not use insert()/upsert() where these invariants matter — they bypass the observers.

## A media `creating` hook stamps owner_directory — no uploader can forget it
`MediaPathGenerator` builds `media/{owner directory}/...` from the media row's own columns, and the owner segment is the `owner_directory` custom property. The application's own upload paths set it (`UpdateProfile\UploadProfileImage`, `Actions\Pets\ResolveMediaOwnerDirectory`), but `Ebess\AdvancedNovaMediaLibrary\Fields\Media` calls `->withCustomProperties($this->customProperties)` with whatever the *field* was configured with — nothing, for all four of ours — so every avatar and pet photo an admin uploaded through Nova permanently lacked it and fell into the generator's database fallback (1 query for a user, 2 for a pet, per owner per request, on the public listing page).

`App\Observers\MediaOwnerDirectoryObserver::creating()` stamps it whenever it is absent, registered from `AppServiceProvider::configureMediaOwnership()`. Adding `withCustomProperties()` to the four Nova fields would have fixed four call sites and nothing about the fifth.

`creating` is the right event: `FileAdder::processMediaItem()` saves the media row and *then* hands it to the filesystem where `getPath()` is first asked, and `MorphMany::save()` fills the morph columns before the insert — so the owner is resolvable and the property lands in the same INSERT, with no second UPDATE.

The lookup itself moved out of the generator into `App\MediaLibrary\OwnerDirectoryResolver`, bound `scoped` so its memo lives one request. A model with no `user()` BelongsTo (Category, Breed) resolves to null with no query and nothing is stamped. Verified live: a Nova avatar upload now writes `{"owner_directory":"894945094270..."}` and path generation costs 0 queries instead of 1.
