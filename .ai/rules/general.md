# General

## Verify to the point where the decision changes; past that, record the strength of your evidence instead of raising it
**This is deliberately the first section in this file, and the position is doing argumentative work.** Twenty-six sections below say *verify harder*, in twenty-six different vocabularies (counted 2026-09-06 by reading the `^## ` headings, not by estimating). Exactly one says when to stop. A stopping criterion placed after twenty verify-harder rules is read by someone already trained by twenty verify-harder rules, so it goes above them or it does not land. Do not "tidy" it further down.

**The rule.** Verification exists to change a decision. Before another round, ask what you would do differently if the check came back the other way. If the answer is *nothing*, the round is not evidence-gathering, it is reassurance — and the honest move is to **record the strength of the evidence you already have** (reported / read / run / measured; on which tree; on which date) rather than spend the round raising it. A claim whose status is written down is re-checkable by the next reader who *does* have a decision riding on it. A claim verified three times and labelled only "confirmed" is not.

**Two specimens, and the pair is the rule** — either one alone reads as an argument for its own direction, and they bound it from opposite sides.

- *Too little.* A dataset's protection was settled by **reading the test source** and reported as established. The counterfactual — break one subject, re-run — was a **two-minute** operation and revealed a property reading structurally could not: deleting one controller's payload key fails **exactly one** of a three-case dataset, with the symptom `Property [reportCategories] does not exist. Failed asserting that false is true.` on the case labelled `with data set "('Home')"`, and the other two green. Reading the file tells you the dataset exists; only breaking one subject tells you it discriminates. The decision *did* turn on it, so the source reading was under-verification. Full write-up in `.ai/rules/tests.md`, "A parameterised test's protection is only as good as its failure localisation".
- *Too much.* **Four transcripts were re-read** to upgrade one claim from *reported* to *confirmed*. The action was identical either way — same wording recorded, same next step. Nothing downstream branched on the status, so the round bought a stronger adjective and no different behaviour. The correct move was one sentence: *reported, not confirmed*, written **inside the rule**, where the next reader meets it at the moment they would otherwise round it up to fact.

**Apply it by the branch, not by your confidence.** The test is *would the answer change what I do*, never *am I sure enough*. Two consequences, pulling opposite ways, both load-bearing:

- Cheap check, answer changes the action → **cheapness is not a reason to skip it.** See the two-minute counterfactual above and "A test that passes against known-broken code is worse than no test" below.
- Expensive check, answer changes nothing → **the deliverable is the hedge, not the check.** Write the status into the rule: `reported, not confirmed`; `read, not run`; `enumerated from the session's own reports, no experiment re-run`. A status written into a report does not survive the session; a status written into a rule is met at the moment it matters.

**This is not licence to say "I judged it wouldn't change anything".** Name the decision in the write-up. *"Not verified further because nothing downstream branches on this"* is checkable by a reader who can see something that does. *"I was confident"* is not.

## The shape of a finding decides where it goes — and a new section has to earn one
`general.md` is globbed `**`, so **every agent in this repo pays for every byte of it before its first edit.** Placement is therefore a cost decision, not a filing preference: **a rule nobody reaches is worth less than no rule, because it consumed the budget a reachable one would have used.**

The symptom, measured 2026-09-06: this file reached **106,146 bytes across 22 sections**, having roughly doubled from ~46 KB inside two hours from a single session's recording, so a `resources/js` task was paying `general.md` + `js.md` ≈ **29k tokens before its first edit**. Growth came almost entirely from new sections, which is why the earning test below exists.

**State it honestly rather than claim a win: the restructure that installed this section did not shrink the file.** Measured the same day, immediately after: `general.md` **121,514 bytes / 27 sections**, `js.md` **25,243**. About **9 KB** of browser-verification instrumentation left for `js.md`, and about **24 KB** arrived — this section, the stopping criterion above it, a backlog of three sections that pass the earning test, and several attachments. The relocation was real and the net was still upward, because a backlog landing is a one-off and the earning test only governs what comes *next*. Re-measure before asserting the trend moved; do not read this paragraph as evidence that it did.

**Triage by glob, first and always.** Content belongs in the file whose glob covers *where the mistake gets made* — see "A rule's glob must cover where the mistake gets made" below. `**` carries only genuinely universal material: review-time discipline, claim discipline, cross-cutting instruments, and PHP/composer toolchain facts this file's `**/*.php` and `composer.json` paths already cover. Subsystem instruments go to the subsystem's file — browser and bundle instrumentation to `js.md`, suite instruments to `tests.md`, schema instruments to `migrations.md`.

**Merging can promote scope, and that is legitimate rather than a loophole.** Two specimens at opposite ends of the stack can be one failure mode, and the merged rule then earns `**` on its merits even though each specimen alone looks subsystem-specific. Worked case, recorded below: `cn`'s tailwind-merge order-sensitivity (view layer) and the `vendor`-symlink autoloader trap (PHP) are one rule — *shared machinery silently alters your result and the call site cannot see it*. Do not split it back out to `js.md` on the strength of one specimen.

**Four shapes. Decide which one you are holding before you write anything.**

1. **Rule → a full section.** Earned **only** by this test: **the failure mode is not covered by an existing section, AND its detection method differs from that section's.** Both clauses, and state the test being applied in your write-up so it stays self-applying. A new failure mode detected the way an existing section already prescribes is a **specimen** of that section. A familiar failure mode found by a genuinely new instrument is usually also a specimen, with the instrument recorded inside that section.
2. **Specimen → attached to the rule it evidences, never a heading of its own.** Keep it **in the finder's own words**, with its measurement and its **symptom strings** intact. A specimen paraphrased into the host section's vocabulary stops being findable by the next person who hits the same symptom, which is the whole of its value.
3. **Measured non-defect → one line in the area's collective `## Measured non-defects` section.** *Do not re-investigate, do not fix.* This is the **only** category here whose value rises as it lengthens: every line is one investigation nobody repeats. Each rule file may carry exactly one such section, in the file whose glob covers the area; `js.md` carries the frontend one today.
4. **Fix → make the edit and write nothing new.** Most findings are this one. A fix that required no judgement teaches nothing and costs every future reader the bytes.

A structure with no home for a given shape turns every future instance of that shape into a new section, which is the growth mechanism this section exists to stop. If you cannot place something, leave it where it is and **say so in your report** — an unhomed finding named out loud is recoverable; one deleted for tidiness is not.

**Promotion — how a specimen becomes a section, in three clauses.**

1. **Attach on first finding.** One instance is a specimen. Hang it on the nearest existing rule and move on.
2. **The finder greps the *symptom* before writing up, and says in the write-up whether it hit.** Not the diagnosis — the error string, the wrong number, the rendered artefact. Then report it either way: *"grepped `Property [x] does not exist` across `.ai/rules`, no hit"* is a recorded null result, and the null result is what makes a later hit meaningful.
3. **Promote when someone holding both findings in view notices the repeat.** Two specimens of one mechanism, hanging off different rules, is the trigger to lift them into a section of their own.

**Its cross-session limit, stated because a mechanism sold as complete gets trusted as complete.** Clause 3 requires a reader holding both findings at once — in practice the orchestrator — and **that reader does not persist across sessions**. The mechanism therefore degrades at every session boundary, and **clause 2 is the only clause that survives one**: the symptom grep is the only part a fresh agent with no memory of the first finding can execute. Fund clause 2 accordingly, and do not rely on clause 3 across a boundary.

**Its failure modes, named:**

- **Paraphrase** — the first finder wrote "the count was wrong"; the second greps `grep -c`. No hit.
- **Anaphora** — the first write-up names its subject by pronoun, so no pattern keyed on the subject's name reaches it. Specimen under "An anaphoric claim defeats a structural grep" below.
- **Different symptom vocabulary** — one defect, two error strings. `Property [reportCategories] does not exist` and a button stuck reading `Loading... Posting...` are the same missing-prop family and share no token.
- **Sections written only in diagnosis language** — the commonest and the worst, because an author who knows the diagnosis titles and writes the section in diagnosis terms, which is exactly the vocabulary a re-finder does not yet have. Hence the standing obligation: **every section carries at least one symptom string** — the thing you would see *before* you knew what it was.

**Read promotion as a partial mechanism with named failure modes, not as a substitute for noticing.** It raises the odds that a repeat is spotted; it does not guarantee it, and no clause here closes the cross-session gap.

## Run Pint with explicit paths, not --dirty, when more than one agent is working
`CLAUDE.md` mandates `vendor/bin/pint --dirty --format agent`. That is sound for a single agent and **wrong for a fleet**: `--dirty` formats every uncommitted file in the tree, not the files the running agent touched. This divergence from CLAUDE.md is deliberate — do not "correct" it back.

Measured this phase: an agent working only in `database/migrations/**` ran `pint --dirty` and applied a `phpdoc_align` change to `app/Actions/Comments/ListCommentSubtreeIds.php`, a file a *different* agent was mid-edit on. That instance was formatting-only; the dangerous versions are an `Edit` failing because content shifted underneath it, or a half-written file being reformatted into something that parses but is not what the author meant.

Rule: when more than one agent may be working concurrently, run `vendor/bin/pint --format agent path/one.php path/two.php` with explicit paths. `--dirty` is fine only for a single agent working alone.

## A rule's glob must cover where the mistake gets made, not where the fix lives
When you record a rule, the glob decides who ever reads it. Scope it to the directories where the mistake gets *written*, not the directory the correct implementation now sits in — those are usually different, and the difference is invisible at the moment of recording, because at that moment you are looking at the fix.

Worked example, cost a live bug: the "walk a comment subtree with ListCommentSubtreeIds, never a frontier loop" rule was filed under `app/Actions/Comments/**` — the home of the Action that *is* the fix. Frontier loops are written in `app/Pipelines/**`, which that glob does not match. A third loop in `app/Pipelines/Pets/Purge/` survived two rounds of the fix and, unlike the two that were replaced, had no cycle guard at all: it spun forever inside an open transaction holding locks. Nobody editing that file was ever shown the rule.

Prefer the widest glob whose files could plausibly contain the mistake, and prefer a wildcard over enumerated directories (`app/Pipelines/**` over `app/Pipelines/Comments/**` + `app/Pipelines/Pets/Purge/**`) — an enumeration re-creates the same gap the moment a fourth flow gets its own directory. If a rule extends an existing section, record it into that section's file so the two stay together.

Second instance this phase of rule *reach* rather than rule *content* being the defect; the first was `index.md`'s preamble telling agents to read only the first matching file. Both were silent: the rule existed, was correct, and was never delivered.

## Establish runtime behaviour by running it, not by reading the source
Four false claims in one close-out shared one root: predicting runtime behaviour instead of observing it. Reading a dependency's source tells you what it *should* do; only running it establishes what it *does*.

- larastan was declared broken from version numbers and vendor source. Running `vendor/bin/phpstan analyse --no-progress` shows it works and reports 145 real errors.
- SSR was declared broken by reading `@inertiajs/vite`'s resolver and reasoning that the `app.ts` fallback exports nothing and must throw. `npm run build:ssr` exits 0 and emits `bootstrap/ssr/app.js` — Inertia v3's simplified SSR has the Vite plugin handle the entry itself. **Scope that reading, because it was later over-read as "SSR works": a build exiting 0 is one render of nothing.** Measured 2026-09-06 by POSTing two captured page objects in a row to a dev server's `/__inertia_ssr`: the first (`Home`) rendered, the second (`auth/Login`) killed the Node process with `localeDirection.ts:41 ReferenceError: document is not defined … at flushJobs` — a module-level `watchEffect` in `app.ts`'s import graph firing from Vue's scheduler, outside every `try`. In development that process is the Vite dev server, so every page after the first took `npm run dev` down (`ERR_CONNECTION_RESET` on every module in the browser). The runtime claim is "renders **twice** in one process", and the instrument is two POSTs, not one build. Fixed in `resources/js/lib/localeDirection.ts`; the rule for the directory is in `.ai/rules/js.md`, "`app.ts` module-level code runs on the SSR server for every request".

Second half of the same rule: absence of the artefact you searched for is not absence of the thing itself. A grep for `DB::transaction` without a `catch` structurally could not find the action that had no transaction at all — the most dangerous one. A coverage check that grepped for a test file named after an Action concluded "no coverage" when the coverage lived in a policy test. **And a formatter-wrapped expression is a shape a single-line grep structurally cannot see — the same class as the `DB::transaction` case above. That mechanism has now missed twice, so what follows is written as a method and not as a warning: for any structural count over `resources/js`, read the block or use a structural matcher. Never `grep -c` a syntax fragment.** The imperative form is deliberate. A warning has to be *remembered at the moment of temptation*; a method *replaces the reflex*, and the second miss below happened to a reader who had already met the warning form of this very sentence.

Both specimens are kept, with their measurements, because the pattern is only visible across the pair — one miss reads as bad luck, two on one mechanism is what forces the imperative.

- A single-line `grep -n 'Math.max(1'` over `resources/js/components/comments/CommentItem.vue` returned nothing (exit 1) while the expression was right there, wrapped by the formatter across `:129-131` — `Math.max(` / `1,` / `(fetchedTotal.value ?? comment.replies_count) - replies.value.length,` — and the work was reported missing on that basis. (`Math.max(` is at `:129` on 2026-09-06; re-grep the identifier, do not trust the number.)
- `grep -c ' as '` over the three `as … | undefined` casts of `resources/js/components/pets/PetListingCard.vue:114-129` counts **2 of 3**, measured 2026-09-06 on this working tree: the `reportCategories` cast is formatter-wrapped across `:122-124`, with `as` ending `:122` and `| SelectOption<ReportCategory>[]` beginning `:123`. Scope that number — the same `grep -c ' as '` over the **whole file** returns **7**, five of them English prose in the docblock, so the count is wrong in both directions at once: it misses a cast and manufactures five. The full write-up of this specimen is under "An anaphoric claim defeats a structural grep" below, where it was first recorded; it is named here too because the pairing is the argument.
- **Third instance, on a new instrument and with a worse output: `git log -S` over a prose fragment that a comment wrapper split.** Establishing whether the false docblock sentence of the second specimen under "A citation proves a claim has a subject" below had ever been committed, `git log --all -S 'able to differ'` returned **nothing, exit 0, no commits** — while the sentence is in `HEAD` and always was. `able to` ends one comment line and `differ` begins the next, so the phrase exists in the file and never on a line. `git log --all -S 'differ from its visible one'` — the same claim, phrased to survive the wrap — returns `91205d6`. Measured 2026-09-06. Two things make this worse than the two bullets above rather than a repeat of them: the instrument is **history, not the tree**, so no amount of re-reading the current file corrects it; and the false answer is **"this never existed"**, which is an answer an agent acts on confidently, where a wrong count at least looks like a number worth re-deriving. It would have downgraded a specimen that is confirmed against a commit to *reported, not confirmed*. So read the imperative above as covering **prose in comments and existence queries over history**, not only counts of syntax over `resources/js`: choose a fragment short enough to sit on one line, or confirm absence by reading `git show <rev>:<path>`.

Its companion is "A search over a corrected artefact is read, not counted" below — the same defect seen from the other side, a count that *finds what is no longer wrong*. Read the two together.

Enumerate the behaviour and ask what covers it, rather than searching for the shape you expect to find.

**The harder half, recorded with its own limits: a written rule does not fire by being written; it fires when the reader frames the question as the one the rule is about.** The `DB::transaction` sweep fired because a reviewer was *looking for the failure mode*. The `Math.max(1` search did not fire because the searcher was looking for a **string** and never framed the question as one of search-completeness — despite having read this section repeatedly in the same session and having been enforcing it on others at the time.

This is **not** a delivery gap in the glob sense and must not be filed as one: the rule reached the reader and still did not reach the moment. The mitigations recorded across this file — recording the check, widening the glob, pointers from the per-directory rule files, citing catches by name — are all about **reach**, and reach turns out not to be sufficient. The imperative rewrite above is a fifth attempt of a *different kind* — it changes the **form** of the rule rather than its delivery, on the theory that a method replaces a reflex where a caution has to be recalled — and it is recorded as an attempt, not as a fix: it was made after the second miss and has not yet been tested against a third. So, plainly: **this failure is not closed by any mitigation recorded here, and none is claimed to close it.** A checklist that admits what it does not cover is more trustworthy than one implying completeness, and a future reader who hits this will recognise it rather than conclude the checklist failed them.

## A claim must say how it was established
Twelve defects in one phase shared a single root: **a claim and its consumer drifting apart, with nothing in the build failing when they disagree.**

Seven of the twelve: a config file whose prose said it was live while the build ignored it; a CSS comment whose hex and HSL disagreed with each other; a "violet-500 cannot carry text" warning contradicted by a component three files away; a contrast ratio measured against a reference the token never uses; a green presence dot for a state the schema deliberately does not track; an agent-instruction file that was wrong about its own build; and one where **no comment existed at all**, which let a wrong model survive two readers.

Five of the twelve were caught by **measurement** rather than by reading. Three had already been written down correctly **elsewhere in the same repo**.

Standing obligation: **every number names the pair it was measured against, and every claim about the build cites the file that proves it.** A claim that says how it was established can be re-checked when its consumer moves; one that does not, silently rots.

A claim that survives verification and one that was never tested are not the same object even when they agree.

**Measure before arguing.** This is a third failure, distinct from the two above: those are about the quality of a measurement that *was* taken — a harness reporting a plausible number about the wrong thing, a claim that does not say how it was established. This one is about not taking a measurement at all. When a decision turns on a quantity, get the quantity before arguing about it. The tell is an argument with a number-shaped hole in it; "that would bloat every feed response" is not a number.

Instance: whether to ship two enum option lists on every feed response, or hide the affordance that needs them, was argued across several rounds by two parties. `strlen(json_encode(...))` over both lists including their prop keys settled it in one step — **540 bytes uncompressed, fixed** (12 option objects across two enums, no dynamic content), so it does not scale with feed size. Neither party asked for the number until an implementer volunteered it. The failure is silent: an unmeasured argument produces a decision that looks identical to a measured one, and only one of the two can be re-checked when the payload changes.

**A comparative claim must name what it is compared against.** "Same", "unchanged", "matches", "identical", "as before" with no referent are **unfalsifiable**, and that makes them worse than a plain error rather than milder: a plain error can be disproved and removed, while an ambiguous claim is agreed with by two readers who disagree with each other and neither of them notices. The reader supplies the missing referent, and they supply the one in front of them, not the one the author meant.

Worked case, established 2026-09-06 by reading the diff and the legacy tree, not by running either. `resources/js/components/notifications/NotificationPanel.vue:51` says of its hand-rolled empty state *"Same two strings, same icon."* Against the `EmptyState.vue` call it replaced — the referent the sentence sits next to, and the one a reviewer reads it against — it is **false**: the icon changed, `BellOff` → `Bell`. Against legacy, which is what the author meant, it is **true**: `/home/asciisd/sites/petconnect-old/resources/js/components/web/NotificationsSheet.vue:219` is `<Bell class="h-6 w-6">`. Reading either source alone yields a confident and opposite answer; only reading both told them apart. The fix is one clause — name the referent and the thing it is *not* being compared to, so a reader who arrives from the diff cannot land on the wrong one. (Still uncorrected as this was written: it is in `resources/js/**` and belongs to that owner, so it is reported, not edited — see "Review what a change REMOVED" on why noticing is not owning.)

**Prove "I changed only comments" mechanically; `git diff` cannot establish it here.** Reverse-apply each edit to reconstruct the before-version, strip comments from both versions, and compare the two results for identity. That is a proof; "I only touched the docblock" is an impression, and the failure it misses — a stray character inside a template, an accidental re-indent of code the docblock sits above — is invisible in a review that trusts the claim. The tree makes the cheap check unavailable rather than merely weaker: every file in this phase already carries unrelated uncommitted changes, so a diff against HEAD mixes your edit with somebody else's and a clean-looking hunk proves nothing about which of you wrote it. Treat this as the expected form of the claim, not as exceptional diligence.

**Re-check embedded `file:line` citations after your final edit, not during.** An agent writing citations into a file is editing the very thing its citations point into, so every subsequent edit in the same pass shifts lines it has already written — the check has to be the last action of the pass, not a step inside it. Re-grep the identifier rather than re-reading the number; this file's own citations moved by 8–10 lines inside an hour for exactly this reason.

**Better still, prefer a file + identifier citation over a `file:line` one, so there is no number to re-check.** A line citation is a standing dependency on every edit anyone makes above it, in a file you do not own and cannot lock; an identifier citation — a function, a const, a prop, a config key, a payload key — travels with the thing it names and cannot drift. Two exceptions, and they are the whole of the judgement. Keep the line where **there is no identifier to name**: one paragraph of a docblock, an HTML comment, one of several identical tags. And keep it where **the number is itself the claim** — a dated reading of a tree is evidence, not a locator, and renumbering it destroys the measurement it recorded.

Established the hard way, sweeping this directory on 2026-09-06: **five wrong line citations across four distinct claims** (one written twice), and **every one of them already named an identifier in the same sentence**, so every one would have survived with the number simply deleted. `optimisticVisitOptions` cited at `:321` when the declaration is at `:327`; `HomeController.php:83-84` for two payload keys that had moved to `:103-104`, in two sections; `PetCardCommentButton.vue:76-85` for a clamp that lives in `countDeleted()`, `:76-85` being the `defineProps` block; and `PetOwnerActions.vue:15` in `js.md` for an import at `:16`. A stale citation inside `.ai/rules` is worse than the same defect in a component docblock, because these files are the artefact that outlives the session and the one agents are explicitly instructed to trust.

## A written gap is a tripwire; an unwritten one is not
That sentence is the rule. The mechanism is what makes it more than an assertion: a recorded gap gives the next agent something to notice an *interaction* with, and an unrecorded one absorbs a widening in silence.

Worked instance. `.ai/rules/enums.md:21` records that every enum `label()` returns hardcoded English with no `__()`, as a deliberately-open gap owned by a scheduled i18n pass. A correct parity fix then moved those English strings onto the **public feed, for every visitor including guests** — the busiest page in the product — where before they surfaced only on pet-detail and profile pages. Nothing about the fix was wrong; what changed is the blast radius of an accepted defect. The agent making the fix could see that, and could say so, **only because the gap was already written down**. Had it not been, the widening would have been invisible: no diff line says "this known-bad string now reaches ten times the traffic".

So the argument for recording an accepted gap is not "so we remember it". It is that an accepted gap is a claim about *how bad* something currently is, and later work routinely changes that number without touching the thing itself. Write the gap down and the next change collides with it; leave it out and the gap quietly gets worse with nobody learning it did.

## The interval between a finding and its fix is a drift window
A distinct drift mechanism from the one this file already catalogues. Everything else recorded here is **a claim outliving its subject** — a docblock, a cross-file citation, a measurement whose importer moved. This is **a queue outliving its premise**: the finding was true when it was written, the world changed, and the finding sat across the change.

Two worked instances, kept as a pair because they resolve in **opposite directions** and the pair is what teaches the shape.

- *Stale by relocation*: a review nit cited `@/lib/commentSurface`. A *different fix in the same remediation round* moved that file to `resources/js/composables/useMutationSurface.ts`, so by the time the nit was briefed it named a path that no longer existed. ## Name the invariant, not the edit
When you brief a change, state the property that must hold afterwards, not the keystrokes. An edit is satisfiable in ways that break the property; an invariant is not. Three catches this phase, and the pattern is only visible across all three:

1. An instruction to remove something from a **guest** branch was satisfiable by a deletion that would also have broken the **authenticated** branch. The edit was well specified; the property "the signed-in path keeps its control" was the thing that had to survive, and only naming it made the difference visible.
2. **Read "removed" as covering what a file *recorded*, not only what it rendered.** A deleted component takes its docblock with it: the invariants it pinned, the alternatives it had already rejected, the reason a value is what it is. Markup that disappears shows up in a screenshot and in a diff someone will read. A rationale that disappears shows up nowhere, and the next agent re-derives it wrongly, or not at all, and then argues the settled question again. The recorded half is the half that dies silently, so it is the half to check first.

**Second half — a capability can be lost by WIDENING a contract as well as by deleting code.** A deletion detector structurally cannot see this: nothing is removed, every existing call site still compiles, the type gets *more* permissive rather than less, and the loss manifests only at a call site that never supplied the value. There is no diff line to notice.

**Operationalise it,** because "be alert to it" gives a reader nothing mechanical. On every diff, enumerate **every prop or parameter that gained a `?`, a `nullable`, or a default**, and for each ask **whether every current mount site or caller supplies it**. That is checkable against a diff.

**The two halves of this section failed in opposite ways, and a reader needs the difference.** The first half was **known and never written down** — a delivery failure, and the *third* instance of exactly what "A rule's glob must cover where the mistake gets made" above already documents (the first was `index.md`'s preamble telling agents to read only the first matching file; the second was the comment-subtree rule filed under the glob where the fix lived, not where the mistake gets written). That this file documents "a rule's glob must cover where the mistake gets made" while a two-phase-old check sat outside the file entirely is both the strongest available argument for that rule and the clearest evidence it does not enforce itself. Recording a rule is a step in the work, not the write-up afterwards.

**Why this lives in one file, and why that file is this one.** Two precedents here pull opposite ways and neither is clean. This file's own standing rule prefers the widest glob whose files could contain the mistake — but it was written against *an enumeration going stale* (three directories, and a fourth flow later got its own), and this defect's surface is not an open-ended set of directories. It is a small, stable set of kinds of declaration: a Vue prop gaining `?`, a PHP parameter gaining a default, a `required` relaxing to `nullable`, a resource key becoming conditional. An enumeration that cannot go stale is not the failure that rule guards against. The other precedent is the deliberate triplication of "A form's read resource and its rules must use identical key names" across `resources.md` / `requests.md` / `concerns.md` with an explicit *"Edit all three together"*. Applied faithfully here that is four or five copies, not three — `js.md`, `app.md`, `requests.md` **and** `concerns.md` (validation rules live in the `PetValidationRules` trait, not in the requests), and `resources.md`. Five copies of a paragraph drift, and a rule about claims drifting apart, living in five drifting copies, would be the worst outcome on the table.

The trade-off stated plainly: **the widest glob maximises nominal reach and may minimise actual reading; triplication maximises reading and minimises durability.** The tie-breaker is *when* each rule is needed. Key-parity is an **edit-time trap** — it bites the person typing in one particular file, so it has to be in front of that person, which is what earns it three copies. This is a **review-time check** run over a whole diff, and the person who needs it is holding a change set rather than a file. No per-directory glob matches "the change I am about to close out"; `**` always does. That is a positive reason for this file, not a default.

The scroll-past problem the key-parity rule was not trusted to survive is real, and it is answered by **pointer, not copy**: `js.md`, `app.md`, `requests.md`, `concerns.md` and `resources.md` each carry a one-line cross-reference to this section. A pointer carries a file name, not a claim, so it cannot fall out of step with what it points at — which is exactly the property five copies would lack. If a pointer ever goes stale it goes stale loudly, because the section it names is either there or it is not.

**Third check, same family — what did your change make FALSE?** The removal check asks what your change destroyed; this asks what it falsified. A change that is entirely correct in itself routinely leaves a true sentence elsewhere untrue: a docblock describing the behaviour you just replaced, a rule quoting a number you just moved, a comment naming a prop you just renamed. Nothing fails, and the sentence keeps being read.

The boundary between fixing that and reporting it is the **causal link, not proximity**: **correct a claim your own change makes false or makes worse; a false claim you merely notice in passing is a finding to report, not a fix to make.** The line is drawn there because it is the only one an agent can actually apply. *Did my edit make this wrong?* is answerable from the diff in front of you. *Is this close enough to be mine?* is not answerable at all, so in practice it resolves to whatever the agent felt like doing, in both directions — a lane violation on one run and an untouched contradiction on the next.

Read it as a **completeness requirement on the change you were already sent to make**, not as an exception to scope discipline. Nothing here widens a task: the claim your change falsified is part of your change in exactly the way the thing your change removed is.

**The two are not always separable, and the clause matters more than the boundary.** If your correction leaves an **uncorrected sibling** that now contradicts the tree, that sibling is yours to **report as urgent** even though you did not write it and must not edit it. You did not make it wrong — you made it *contradictory*, which is a different and worse defect. Worked case, this phase, **reported by the agent that hit it rather than re-observed here**: two header docblocks were correctly rewritten and cited `resources/js/components/messaging/MessagesDropdown.vue:131` and `:139-143` as their evidence, which turned an ordinary stale sentence at `MessagesDropdown.vue:26-29` into a direct contradiction of two freshly-corrected files that name its own file by line. Stale before, contradicted after — and the second is the worse of the two, for the reason in the next paragraph.

Re-read on 2026-09-06 while recording this, and the re-read is part of the lesson: `:131` is `const canRead = computed(() => viewer.value?.email_verified_at != null);`, `:139-143` is the `onMounted` that calls `ensureLoaded()` under it, and the docblock at `:26-29` now **agrees** with both. So either the sibling was corrected in the interval or the citation has moved, and this pass could not tell which from the tree alone. Keep the case — the mechanism is what earns its place, and it does not depend on the instance still being live — but read the line numbers as the reporter's, taken on a tree several agents were writing to. This is the drift window above in miniature, arriving while a rule about it was being written.

**A partial correction can leave the tree worse than no correction — which is why the clause above is urgent rather than tidy-up.** A lone false comment is a defect a reader may simply believe: bad, but it fails in one direction and a later reader can still disprove it. A false comment **contradicted by a corrected sibling** forces the reader to adjudicate, and readers do not adjudicate neutrally — they resolve toward the file they are editing, which is the uncorrected one. The half-done correction can therefore hand the wrong claim *more* authority than the whole-done nothing would have.

The remedy is not to correct less. It is to **enumerate every instance of a claim before correcting any of them** — grep the claim, not the file — and to treat "found in three files, fixed one" as **unfinished, not scoped**. This is the search-completeness discipline of "Establish runtime behaviour by running it, not by reading the source" above, pointed at a *write* instead of at a read; the write side is the worse of the two, because a missed instance in a read costs you a wrong belief while a missed instance in a write costs every later reader theirs. Where you genuinely cannot fix them all — the remaining copies are another agent's files — the enumeration itself is the deliverable: report every instance by path and line, as the urgent item above, rather than reporting the one you fixed.

**Specimen, and it is this corollary's own shape landing on the durable artefact — inside two hours of the corollary being recorded.** `resources/js/components/pets/card/PetCardHeader.vue` was scoped by its owner; three sentences in **this file** described the state before that fix, and correcting some of them without the others would have left `.ai/rules` — the artefact agents are explicitly told to trust — asserting a defect that no longer exists. Two of the three had gone false ("still carries the narrower premise", "the sentence is still unscoped", both rewritten in place above) and **one was still true and had to be left alone**: "the narrow claim is still there and still correct" survives, because the sentence was *scoped*, not changed. Read that as the operative detail rather than a footnote — the instances of a claim family do not all fall the same way, so "consistently update all three" is as wrong as fixing one, and each instance has to be checked against the primary text on its own.

Two things it teaches beyond the general form. First, **a rule file asserting a defect that has been fixed is worse than one silent about it**: it does not merely misinform, it *dispatches* — the next reader goes and fixes something already correct, which here would have meant re-scoping a docblock that already carries the clause, in another agent's lane. Second, the uncorrected instances were in `.ai/rules` itself. Every other worked case in this section has the stale copy in a component; this one had it in the file that adjudicates the others, which is where a contradiction has the most authority and the least chance of being disproved by the tree.

## record-rule appends and never merges: create with it, merge with Edit, then verify
Two structural limits of the Boost `record-rule` MCP tool, and the authoring sequence they force. Both were first read out of `vendor/laravel/boost/src/Rules/RuleRepository.php` and then **re-established by running `RuleRepository` against a scratch directory** — per "Establish runtime behaviour by running it" above, reading the source only tells you what it should do.

**Limit 1 — `record-rule` appends; it does not merge.** `appendEntry()` (`RuleRepository.php:307-312`) does `File::put($contents."\n\n## ".$title."\n".$note."\n")` unconditionally, and `write()` calls it on every path (`:130`). Nothing anywhere looks for an existing heading. Passing an **existing heading verbatim therefore produces a second, identical `## heading` at the end of the file** — and the call returns the file path and reports success. Ran it: two `write('app/Models/**', 'Alpha rule', …)` calls into a scratch directory left a single `models.md` containing `## Alpha rule` twice, one entry under each.

That is the worst failure this particular tool could have. "Extend the existing section rather than append a near-duplicate" is standing guidance here — see "The interval between a finding and its fix is a drift window" above, and `.ai/rules/routes.md` on why a stale justification sitting beside a corrected one is how a correction gets reverted. An agent following that guidance reaches for `record-rule` with the existing heading, receives success, reports success, and leaves a duplicate heading behind in the file whose entire subject is claims drifting apart from each other. Green report, silent failure, and the damage is exactly the thing the guidance existed to prevent.

**Limit 2 — `areaKey()` collapses every dotted root-level glob to the empty area.** `meaningfulSegments()` (`:257-264`) drops any path segment containing `*` **or `.`**, and `areaKey()` (`:249-252`) joins whatever survives. A root-level filename is a single dotted segment with no directory in front of it, so nothing survives and the area is `''` — the same area as `**`. Measured by running `areaKey()` through reflection: `**`, `**/*.php`, `composer.json`, `composer.lock`, `vite.config.ts` and `phpstan.neon` all return `''`; `config/media-library.php` returns `config`; and `.ai/rules/**` returns `rules`, because `.ai` is dotted and disappears too.

The consequence, also run rather than reasoned: `resolveTargetFile()` (`:184-191`) returns the **first** rule file holding any path in the same area, so once one file carries `**` every later dotted root-level glob lands in that file whatever the author intended. In the scratch run, `vite.config.ts`, `phpstan.neon` and `composer.json` all appended to `general.md` and silently grew its frontmatter. An empty rules directory is no better: `uniqueFilePath()` falls through to the literal `'general'` candidate (`:226-228`) because there are no meaningful segments left to slug, so a first-ever rule for `composer.json` still creates `general.md`. In this repo `general.md` is the file that carries `**`, and the only rule files sorting ahead of it are `actions.md`, `app.md`, `comments.md`, `concerns.md`, `config.md`, `controllers.md`, `data.md`, `enums.md` and `factories.md` — none of which holds an empty-area path. So today every dotted root-level glob resolves to `general.md`. `.ai/rules/vite.md` has `paths: [vite.config.ts]` and `record-rule` demonstrably cannot have produced it (it was created some other way, by hand or by a later frontmatter edit); a `record-rule` call with that glob today appends to `general.md` instead, because the empty-area match on `general.md` is tested before `vite.md`'s exact-glob match is ever reached. If a dotted root-level file needs its own rule file, create the file and its frontmatter with `Write`/`Edit` and keep `record-rule` out of it.

**The sequence these force is three steps, not one.**

1. **`record-rule` to create a new section.** Creating is the only operation it performs correctly.
2. **`Edit` to merge into a section that already exists.** Never `record-rule` with an existing heading — see Limit 1. The same goes for frontmatter: growing an existing file's `paths` is an `Edit`.
3. **Verify afterwards, by inspection.** No rule file contains a duplicate `## ` heading, and `index.md` still maps every rule file. The shape is `grep -c '^## '` per file plus a duplicate-heading sweep over the directory — `for f in .ai/rules/*.md; do grep '^## ' "$f" | sort | uniq -d | sed "s|^|$f: |"; done`, where silence is the pass — and `comm -13` between the rule files on disk and the paths named in `index.md`.

**An agent that stops at step 1 has not finished the job.** Step 3 is required *regardless of whether you believe you had the directory to yourself*, because verification is also the only thing that catches a concurrent writer. Do not assume exclusivity: seven rule files were rewritten during one agent's read phase by a different agent finishing a pointer pass, under an explicit guarantee of exclusivity that was simply unenforceable. ## Two workstreams on the same lines get a third owner, not a priority order
When two workstreams need to change the same lines, do not resolve it by ranking them. Give the shared surface a **third owner** — one task neither workstream runs, whose output both inherit as input.

The argument is mechanical rather than stylistic, which is why "just tell them who goes first" keeps not working. **A priority order between peers is only executable if each peer knows the other's state**: "B waits for A" requires B to observe whether A has finished, and that is exactly the information neither of them has about the other. What the pair actually does is either both wait — the deadlock shape — or both write, which is the concurrent-writer hazard "record-rule appends and never merges" records above, where `appendEntry()` is an unlocked read-modify-write (`RuleRepository.php:307-312`) and the loser's write vanishes with no error. **Ownership requires no shared state; precedence does.**

Worked case this phase, reported by the coordinator rather than observed here: two review gates both required the same two header docblocks rewritten, and neither could proceed on a file the other might be mid-edit on. A single shared-surface task, owned by neither gate and run once, produced the rewrite; both gates then read it as input and closed against it. Cost: one extra task. What it bought: no ordering assumption anywhere, and no version of those files that only one gate had seen.

**Symptom vocabulary, because this section is written entirely in diagnosis language and a re-finder will not arrive holding the words "shared surface".** What you actually see: an `Edit` failing because the content shifted underneath it; a file reformatted mid-write by somebody else's `pint --dirty`; two agents both reporting success with only one write present; or two tasks each waiting for the other to finish and neither able to observe that the other has.

Two consequences worth stating, because the shape recurs. The third owner must be given the *union* of what both workstreams need from those lines, or it ships a rewrite one gate then has to redo — which reintroduces the shared surface it was created to remove. And `.ai/rules/general.md` is itself a shared surface by construction: every `**` glob resolves to it (see the `areaKey()` limit in "record-rule appends and never merges" above), so a phase where several agents have rules to record into it wants **one recorder holding the whole set**, not a queue of appenders.

## A claim that is true only within a scope must state the scope
The companion to "A citation proves a claim has a subject, not that the claim is true of it" above, and the reason that specimen's narrow claim got mis-generalised in the first place: **it never said why it was narrow.**

With that clause present, carrying the claim across to `pr-6` versus `pe-6` is visibly out of scope, because `padding-right` is the element's own property and the clause does not cover it.

General form: **a claim that is true only within a scope should state the scope, or it will be applied outside it.** A reader holding only the observation has no way to tell a narrow truth from a wide one, and the wide reading is the more useful-sounding of the two, so the wide reading is the one that travels. The cost of prevention is a clause; the cost of omission is the five-link chain in the section above, which ended one step short of replacing a correct sentence with a wrong one.

This sharpens rather than replaces the standing obligation under "A claim must say how it was established" that every number names the pair it was measured against. That one is about *how* a claim was established; this one is about *where* it holds. A claim can state its method exactly and still be silent on its boundary, and the silence is what gets it re-used somewhere it is false.

**Rewritten in place 2026-09-06, because this line had gone false: the sentence is now scoped.** It used to read *"Re-read 2026-09-06: the sentence is still unscoped. ## An anaphoric claim defeats a structural grep: bound the search with a pattern, close it with a block-level read
A structural sweep for a claim *family* — a pattern over the shape of the assertion rather than over a handful of guessed phrasings — is a much stronger test than seeded phrasings, and preferring it is correct. **What it buys is a better-bounded enumeration, not a closed one**, and the gap is mechanical rather than a matter of care.

**"Exhaustive" overstates what a structural argument buys, and this is the wording that survives instead.** The argument behind the sweep was genuinely strong and is worth keeping in full: a sentence in this family has to name **both** a fetch and a guard, and every guard in the tree uses one of a known set of predicate identifiers, so a pattern built over those identifiers cannot miss a sentence that names one. That is a real improvement over guessing phrasings, and it is still **defeated by the specimen below** — a sentence that names its subject by pronoun matches no pattern keyed on the subject's name, whichever identifier set the pattern is built from. So the claim to make is *bounded*, never *closed*: the structural pattern reduces the candidate set from "every file" to "these files", and the block-level read of those files is the only thing that closes it.

## A test that passes against known-broken code is worse than no test: the intercept stage IS the experiment, so run the counterfactual
A green harness is a claim like any other, and it says how it was established or it rots — except this one rots silently and *reassuringly*, which is why it earns its own entry rather than a line under "A claim must say how it was established".

**Worked case, with the recipe, because the recipe is what makes it repeatable.** An experiment was built to prove that a write landing **during an in-flight fetch** still appears — the race the fix was for. It held the fetch at the **request** stage. So the server did not run its query until after the hold was released, by which time the write had committed: the held response already carried the new row, the assertion passed, and **the unfixed code passed it too**. The experiment could not fail. It was caught only by running the **counterfactual** — the same experiment against the code before the fix — which is the control that separates "the behaviour is correct" from "the harness cannot see the behaviour".

**The general form is the sentence to carry away: when an experiment involves holding, delaying or intercepting anything, *which stage you intercept at is the experiment*, not an implementation detail of it.** Request-stage, response-stage, post-query, post-commit and pre-render holds all look like "pause the fetch" in the test's prose and prove entirely different propositions. Write the stage into the test name or its docblock, next to what it is supposed to prove, so a reader can check the two match. The same applies to a fake, a `Http::fake()`, a queue `sync` swap or a `DB::listen` probe: each one relocates the seam, and the seam decides what is observable.

**And always run the A/B.** Break the fix — revert it, comment the line, stub the guard — and re-run. **A green result on known-broken code is the only reliable signal that the harness is measuring something other than what you think**, and it is cheap: one revert, one run, one revert back. Nothing else distinguishes a passing test from a test that cannot fail; not review, not coverage, and least of all a green suite. This is the "Measure before arguing" discipline pointed at the instrument instead of at the subject, and it is the same move that established the RTL clearance measurement above — the broken arrangement was rendered too, and produced a different number.

**The safety recipe for breaking the code, recorded here rather than left implicit, because without it the paragraph above is aspirational.** "Revert the fix and re-run" is not followed by an agent working in a live tree alongside other agents unless doing so is *known* to be safe, and nobody writes that procedure down at the moment they need it. So:

1. Guard on `git status --porcelain <path>` for the file you are about to break. **Abort if it is already modified** — you cannot restore what you did not start from.
2. Confirm no live agent writes that path. This is the concurrent-writer hazard "Run Pint with explicit paths, not --dirty" above records, with a destructive edit instead of a formatter.
3. Run the break, the test and the restore as a **single atomic command**, so the window in which the tree is modified is seconds rather than however long you spend reading output.
4. Restore with `git checkout -- <path>` against a known commit — **never** by re-editing the file back. A re-edit is a reconstruction that can differ, and it differs silently.
5. Verify `git status --porcelain <path>` is silent afterwards. The restore is not done until it has been checked, for the same reason step 3 of "record-rule appends and never merges" above is not optional.
6. **Only on committed files.** A committed file makes restoration exact; an uncommitted one makes it reconstructive, and an untracked one makes `git checkout --` fail outright. Live illustration on this tree, 2026-09-06 at HEAD `7bc4271`: `app/Http/Controllers/Web/HomeController.php` is clean and committed and passes the guard, which is why the counterfactual under `.ai/rules/tests.md`, "A parameterised test's protection is only as good as its failure localisation", could be run against it; `app/Providers/AppServiceProvider.php` is modified and would fail step 1, and `tests/Feature/CommentsDialogPropContractTest.php` is untracked and has nothing to restore to.

**The cost-benefit is what makes this mandatory rather than optional, so state it as a number and not as a preference: the whole procedure is a two-minute operation.** Against that, stopping at a source reading when the counterfactual is nearly free is precisely where the surprises live. The localisation property measured in `.ai/rules/tests.md`, "A parameterised test's protection is only as good as its failure localisation" — that breaking one controller fails exactly the one dataset case named after it, and leaves the other two green — **was invisible to reading the test and appeared only under execution**. Reading the file tells you the dataset exists; only breaking one subject tells you the dataset discriminates. Two minutes is not a budget worth defending.

That recipe covers breaking *source*. Breaking *rendered* behaviour has its own isolation recipe — rsync to a copy outside the repo, symlink `vendor` and `node_modules`, drop `public/hot` — under "Amplification toward inaction" above. Both exist for the same reason: the counterfactual must not be the thing that damages the tree.

Worth stating plainly for prioritisation: **a test that passes against known-broken code is worse than no test at all.** No test leaves the risk visible and unclaimed. A test that cannot fail retires the risk in everyone's head, discourages the next agent from re-checking the behaviour, and will be cited as evidence the bug is fixed the next time it recurs.

**Symptom vocabulary, because this section is otherwise written entirely in diagnosis language.** What you actually see is a **green run you did not expect to be green**, a harness whose prose says "pause the fetch" without saying where, or an assertion that holds both before and after the fix. If the A/B produces the same result on both arms — no failure, no diff — you are looking at the instrument, not the subject.

**Evidence this rule fires, recorded briefly because until now every rule in this corpus was evidence of a failure.** An agent holding this section **named its intercept stage unprompted**, in its own words: *"the stage is named because it is the experiment."* That is the general form above being applied rather than recalled — the naming happened at write-up time, without anyone asking for it. Its sibling, an agent retaining its run files and mechanically diffing every quoted value against them, is recorded under "A quoted measurement is diffed against the run that produced it" below.

## A compound claim is verified clause by clause: the true half vouches for the false one
**When a claim bundles a mechanism with a location, verify each independently.** A citation establishes that a claim has a *subject*; it does not establish that every clause is true *of* that subject. A conjunction of two true parts can be false, and this is the shape that gets past review, because the half a reviewer checks is the half that holds and it lends its credibility to the other.

**Worked case, and it is this file's own record.** The specimen under "An anaphoric claim defeats a structural grep" above said, in one sentence, that the file holding three `as ... | undefined` casts was the file carrying an anaphoric sentence. Both halves were true — there *was* an anaphoric sentence (`resources/js/components/pets/card/PetCardActions.vue`, *"no page that renders a card ships **the first**"*) and there *is* a file holding three unsafe casts (`resources/js/components/pets/PetListingCard.vue:114-129`, which carried its own separate false sentence, *"`Home` ships none"*) — and the conjunction joining them was false. It travelled with file citations attached, which is exactly what makes a claim look verified. Corrected in place 2026-09-06.

**Note what this is: the citation rule firing on the person who recorded it, in the same session.** "A citation proves a claim has a subject, not that the claim is true of it" is a section of this file, and the compound claim it now catches was written by an agent that had just recorded it. Knowing the rule is not the same as framing the question as the one the rule is about — the limit already recorded under "Establish runtime behaviour by running it, not by reading the source". So the mitigation has to be mechanical rather than attitudinal: **split the sentence into its clauses and check each against the primary text**, and treat *mechanism + location* as two claims wearing one citation.

**The correct handling is recorded as the model, because an agent met this and got it right.** It could not confirm the briefed wording of the false sentence — `git log --all -S 'ships the first'` returns nothing, so it never reached a commit — so it recorded **the mechanism as established and the wording as reported**, and wrote that limitation *inside the rule* rather than into a report that would not survive the session. That is what a hedge looks like when it is written where it is needed: the next reader meets the status at the moment they would otherwise upgrade it to fact.

**A second shape of the same defect: ambiguity relayed as a clean assertion.** Distinct from the compound case above and recorded beside it because the two are told apart by one question. In the compound case **both clauses were true and the conjunction was false**. Here the source sentence was **internally inconsistent** — it named `card-action` in one clause while asserting `card-title` was the load-bearing one — and the relay **compressed it into a single clean claim**, choosing one of the two readings and dropping the inconsistency along with it. Nothing downstream could tell that a choice had been made: a resolved ambiguity and an unambiguous source are the same object in the text, exactly as a recalled measurement and a taken one are.

**The clause: resolving an ambiguity is an act of authorship, and it is attributed to the resolver, not to the source.** Write *"the source says `card-action` in one clause and `card-title` in another; I read it as X because Y"*. Do not write *"the source says X"*. The tell is mechanical and needs no judgement about intent: **you had to pick, and the sentence you produced does not say you picked.** Symptom vocabulary — two different identifiers for one subject inside one sentence; a relayed claim that is *cleaner* than the source it is relaying.

## Sequence what feeds a decision: a verdict requested in parallel with the action is decorative
**Parallelism is correct for independent work and wrong when one branch is the input to the other's decision.** Fanning out saves time only where nothing downstream is already assuming a result. Where a step cannot legitimately be taken until a result arrives, running the request alongside the step does not overlap two pieces of work — it deletes one of them.

**Worked case, reported by the coordinator that ran it rather than observed here.** A coordinator ran its own gates and requested a reviewer's verdict **concurrently**, then acted on its own gates. The verdict was still **open** when the action went out; the action assumed it **closed**. Nothing in that arrangement could have surfaced a dissenting verdict — by the time it arrived there was nothing left for it to change — so the requested review was decorative before it was answered, and a report naming both the gates and the review reads exactly like one where the review mattered.

**Same family as the wrong-stage intercept recorded above** ("A test that passes against known-broken code is worse than no test"), and they belong together: in both, **the structure of the procedure decided the outcome and the evidence never got a chance to bear on it**. One holds the fetch at a stage where the fix cannot matter, so the experiment cannot fail; the other acts before the verdict, so the verdict cannot matter. Neither is a misjudgement *about* evidence — both are arrangements in which no evidence would have changed anything, which is why reviewing the conclusion catches neither. The wrong-stage version at least leaves a green harness somebody can re-run; this one leaves nothing at all, in the way "Amplification toward inaction" above describes an unattempted check leaving no artefact.

**The tell is mechanical, so use it as one: you can predict the outcome without reading the pending result.** When that is true of a branch you are about to run in parallel, sequence it — request, wait, then act — and fan out only the branches whose outputs nothing downstream has already assumed. If waiting is genuinely too expensive, the honest form is to act and say the verdict was not consulted, not to request it and imply it was.

## An output wider than its subject cannot answer a question about the subject: --name-only, not --stat
**Before trusting a check, ask whether its output contains anything other than the thing being asked about.** An output that is a *superset* of its subject cannot answer a question about the subject, because a hit no longer distinguishes the artifact from prose about the artifact.

**Worked case, measured 2026-09-06 and re-runnable on this repo at HEAD `7bc4271`.** To check whether `app/Providers/AppServiceProvider.php` had been excluded from a commit, `git show --stat 7bc4271 | grep AppServiceProvider` **returns a hit — and the file is not in the commit.** `--stat` renders the commit *message* above the file table, that message carries an exclusion note naming the file, and the grep cannot tell the two apart. The instrument that answers the question actually asked is `git show --name-only --format= 7bc4271 | grep AppServiceProvider`, which emits paths only, exits **1**, and does so against the 85 paths that commit really touches. Same repo, same sha, same grep, opposite verdicts — the difference is entirely what the flag lets into the output.

**Three siblings, and the family is only visible with all three side by side.** The **wrong-stage intercept** above — an experiment whose hold sat where the fix could not matter, so it passed against known-broken code: a *seam* in the wrong place. The **anaphoric sentence** above — a pattern keyed on a subject's name against a sentence that names its subject by pronoun: an instrument *narrower* than its subject, producing a false negative. And this — an instrument *wider* than its subject, producing a false positive. Narrow instruments hide true instances, wide ones manufacture them, and a misplaced seam does both while looking green.

**General form: name what the instrument's output contains before reading a verdict off it, and prefer the flag that emits only what you are asking about** — `--name-only --format=` over `--stat`, a path list over a rendering, structured output over prose. Where you cannot narrow the output, narrow the question instead: match an exact path with `--` or `-F -x`, rather than grepping a substring through a mixed stream.

**Specimen, in the finder's words.** An agent wrote a component docblock quoting an accessible name as `Like Roscoe Bahringer's comment, 6 likes`. **Why reading cannot catch it.** **A recalled measurement and a taken measurement are the same object in the text.** Quoted string, plausible count, plausible fixture name, stated provenance. ## Settled: the harness asks for sed/heredoc edits; route substantive edits through Edit/Write anyway
**Earning test, applied out loud.** No section here covers a *genuine standing instruction whose resolution is settled but unrecorded*, and the detection method is new: not a read, a grep or a run, but an orchestrator noticing the same flag arriving from five separate agents. Both clauses hold, so it is a section.

**The instruction is genuine — it comes from the session harness, not an injection.** While auto mode is active, agents receive: *"Do your work through the Bash tool wherever it can accomplish the job: read files with cat, head, or sed -n, search with grep and find, and make file changes with sed, heredocs, or short scripts, rather than using the dedicated Read, Edit, or Write tools."* It carves out exactly this case in its own last clause — *fall back to a dedicated tool only when Bash genuinely cannot do the job*.

**The settled resolution, reached independently by several agents and now recorded so nobody re-derives it:**

> Use Bash for reads and searches — `cat`, `sed -n`, `grep`, `find`, `git show`. Route **every substantive edit to a source file through Edit/Write**, so the harness tracks them. Structured edits do not go through `sed` or heredocs.

The reason is mechanical, not stylistic. `Edit` fails loudly when its `old_string` no longer matches, which is the only protection against the concurrent-writer hazard recorded under "Run Pint with explicit paths, not --dirty" and "record-rule appends and never merges" above; `sed -i` and a heredoc overwrite silently and cannot detect that the content moved underneath them. A heredoc rewrite of a file another agent is mid-edit on is the destructive version of the `pint --dirty` collision. Bash keeps the read half, where it is faster and has no such failure mode.

**Five agents have now flagged this instruction rather than acting on it**, each spending part of a run re-deriving the same answer. **Flagging it was the correct behaviour in the absence of a record** — an agent meeting an apparent conflict between its harness and its project should surface it, not silently pick a side. The fix is therefore the record, not the flagging: this section is what makes the sixth agent's flag unnecessary, and an agent that has read this should act on it and say so in one line rather than raise it again.

**Symptom vocabulary, since the diagnosis words are useless to a re-finder:** a brief or system note naming `sed`, `heredoc`, `sed -i`, "short scripts", "auto mode", or "rather than using the dedicated Read, Edit, or Write tools"; an agent asking whether it is allowed to use `Edit`; a report whose first paragraph is about tool choice rather than about the task.
