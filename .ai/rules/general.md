# General

## Laravel 13 dependency floors: medialibrary 11.23.5, Nova 5.8, ebess 5.2
Version floors worked out during the Laravel 13 port — do not "correct" them.

- `spatie/laravel-medialibrary`: **v12 does not exist**. 11.23.5 is the first release accepting `illuminate/* ^13.0` (11.20.0 still caps at `^12.0`). Require `^11.23.5`, not `^12`.
- `laravel/nova`: needs **>= 5.8.0** for Laravel 13. Nova 5.0–5.7.x cap at `laravel/framework ^12.1.1`. Nova also requires the `https://nova.laravel.com` composer repository declared in `composer.json`, with licence credentials in `~/.config/composer/auth.json` (never committed).
- `ebess/advanced-nova-media-library`: **5.2** is the first Laravel 13-compatible release. Known future blocker: it still pins `spatie/laravel-medialibrary ^8 – ^11`, so the day medialibrary ships v12 this package will block the upgrade until it widens the constraint.

## Run Pint with explicit paths, not --dirty, when more than one agent is working
`CLAUDE.md` mandates `vendor/bin/pint --dirty --format agent`. That is sound for a single agent and **wrong for a fleet**: `--dirty` formats every uncommitted file in the tree, not the files the running agent touched. This divergence from CLAUDE.md is deliberate — do not "correct" it back.

Measured this phase: an agent working only in `database/migrations/**` ran `pint --dirty` and applied a `phpdoc_align` change to `app/Actions/Comments/ListCommentSubtreeIds.php`, a file a *different* agent was mid-edit on. That instance was formatting-only; the dangerous versions are an `Edit` failing because content shifted underneath it, or a half-written file being reformatted into something that parses but is not what the author meant.

Rule: when more than one agent may be working concurrently, run `vendor/bin/pint --format agent path/one.php path/two.php` with explicit paths. `--dirty` is fine only for a single agent working alone.

## A rule's glob must cover where the mistake gets made, not where the fix lives
When you record a rule, the glob decides who ever reads it. Scope it to the directories where the mistake gets *written*, not the directory the correct implementation now sits in — those are usually different, and the difference is invisible at the moment of recording, because at that moment you are looking at the fix.

Worked example, cost a live bug: the "walk a comment subtree with ListCommentSubtreeIds, never a frontier loop" rule was filed under `app/Actions/Comments/**` — the home of the Action that *is* the fix. Frontier loops are written in `app/Pipelines/**`, which that glob does not match. A third loop in `app/Pipelines/Pets/Purge/` survived two rounds of the fix and, unlike the two that were replaced, had no cycle guard at all: it spun forever inside an open transaction holding locks. Nobody editing that file was ever shown the rule.

Prefer the widest glob whose files could plausibly contain the mistake, and prefer a wildcard over enumerated directories (`app/Pipelines/**` over `app/Pipelines/Comments/**` + `app/Pipelines/Pets/Purge/**`) — an enumeration re-creates the same gap the moment a fourth flow gets its own directory. If a rule extends an existing section, record it into that section's file so the two stay together.

Second instance this phase of rule *reach* rather than rule *content* being the defect; the first was `index.md`'s preamble telling agents to read only the first matching file. Both were silent: the rule existed, was correct, and was never delivered.

## Establish runtime behaviour by running it, not by reading the source
Four false claims in one close-out shared one root: predicting runtime behaviour instead of observing it. Reading a dependency's source tells you what it *should* do; only running it establishes what it *does*.

- larastan was declared broken from version numbers and vendor source. Running `vendor/bin/phpstan analyse --no-progress` shows it works and reports 145 real errors.
- SSR was declared broken by reading `@inertiajs/vite`'s resolver and reasoning that the `app.ts` fallback exports nothing and must throw. `npm run build:ssr` exits 0 and emits `bootstrap/ssr/app.js` — Inertia v3's simplified SSR has the Vite plugin handle the entry itself.

Second half of the same rule: absence of the artefact you searched for is not absence of the thing itself. A grep for `DB::transaction` without a `catch` structurally could not find the action that had no transaction at all — the most dangerous one. A coverage check that grepped for a test file named after an Action concluded "no coverage" when the coverage lived in a policy test. A single-line `grep -n 'Math.max(1'` over `resources/js/components/comments/CommentItem.vue` returned nothing (exit 1) while the expression was right there, wrapped by the formatter across `:129-131` — `Math.max(` / `1,` / `(fetchedTotal.value ?? comment.replies_count) - replies.value.length,` — and the work was reported missing on that basis. A formatter-wrapped expression is a shape a single-line grep structurally cannot see — the same class as the `DB::transaction` case above. Enumerate the behaviour and ask what covers it, rather than searching for the shape you expect to find.

**The harder half, recorded with its own limits: a written rule does not fire by being written; it fires when the reader frames the question as the one the rule is about.** The `DB::transaction` sweep fired because a reviewer was *looking for the failure mode*. The `Math.max(1` search did not fire because the searcher was looking for a **string** and never framed the question as one of search-completeness — despite having read this section repeatedly in the same session and having been enforcing it on others at the time.

This is **not** a delivery gap in the glob sense and must not be filed as one: the rule reached the reader and still did not reach the moment. The mitigations recorded across this file — recording the check, widening the glob, pointers from the per-directory rule files, citing catches by name — are all about **reach**, and reach turns out not to be sufficient. So, plainly: **this failure is not closed by any mitigation recorded here, and none is claimed to close it.** A checklist that admits what it does not cover is more trustworthy than one implying completeness, and a future reader who hits this will recognise it rather than conclude the checklist failed them.

## A claim must say how it was established
Twelve defects in one phase shared a single root: **a claim and its consumer drifting apart, with nothing in the build failing when they disagree.**

Seven of the twelve: a config file whose prose said it was live while the build ignored it; a CSS comment whose hex and HSL disagreed with each other; a "violet-500 cannot carry text" warning contradicted by a component three files away; a contrast ratio measured against a reference the token never uses; a green presence dot for a state the schema deliberately does not track; an agent-instruction file that was wrong about its own build; and one where **no comment existed at all**, which let a wrong model survive two readers.

Five of the twelve were caught by **measurement** rather than by reading. Three had already been written down correctly **elsewhere in the same repo**.

Standing obligation: **every number names the pair it was measured against, and every claim about the build cites the file that proves it.** A claim that says how it was established can be re-checked when its consumer moves; one that does not, silently rots.

A claim that survives verification and one that was never tested are not the same object even when they agree.

**Measure before arguing.** This is a third failure, distinct from the two above: those are about the quality of a measurement that *was* taken — a harness reporting a plausible number about the wrong thing, a claim that does not say how it was established. This one is about not taking a measurement at all. When a decision turns on a quantity, get the quantity before arguing about it. The tell is an argument with a number-shaped hole in it; "that would bloat every feed response" is not a number.

Instance: whether to ship two enum option lists on every feed response, or hide the affordance that needs them, was argued across several rounds by two parties. `strlen(json_encode(...))` over both lists including their prop keys settled it in one step — **540 bytes uncompressed, fixed** (12 option objects across two enums, no dynamic content), so it does not scale with feed size. Neither party asked for the number until an implementer volunteered it. The failure is silent: an unmeasured argument produces a decision that looks identical to a measured one, and only one of the two can be re-checked when the payload changes.

**A comparative claim must name what it is compared against.** "Same", "unchanged", "matches", "identical", "as before" with no referent are **unfalsifiable**, and that makes them worse than a plain error rather than milder: a plain error can be disproved and removed, while an ambiguous claim is agreed with by two readers who disagree with each other and neither of them notices. The reader supplies the missing referent, and they supply the one in front of them, not the one the author meant.

Worked case, established 2026-09-06 by reading the diff and the legacy tree, not by running either. `resources/js/components/notifications/NotificationPanel.vue:51` says of its hand-rolled empty state *"Same two strings, same icon."* Against the `EmptyState.vue` call it replaced — the referent the sentence sits next to, and the one a reviewer reads it against — it is **false**: the icon changed, `BellOff` → `Bell`. Against legacy, which is what the author meant, it is **true**: `/home/asciisd/sites/petconnect-old/resources/js/components/web/NotificationsSheet.vue:219` is `<Bell class="h-6 w-6">`. Reading either source alone yields a confident and opposite answer; only reading both told them apart. The fix is one clause — name the referent and the thing it is *not* being compared to, so a reader who arrives from the diff cannot land on the wrong one. (Still uncorrected as this was written: it is in `resources/js/**` and belongs to that owner, so it is reported, not edited — see "Review what a change REMOVED" on why noticing is not owning.)

**Prove "I changed only comments" mechanically; `git diff` cannot establish it here.** Reverse-apply each edit to reconstruct the before-version, strip comments from both versions, and compare the two results for identity. That is a proof; "I only touched the docblock" is an impression, and the failure it misses — a stray character inside a template, an accidental re-indent of code the docblock sits above — is invisible in a review that trusts the claim. The tree makes the cheap check unavailable rather than merely weaker: every file in this phase already carries unrelated uncommitted changes, so a diff against HEAD mixes your edit with somebody else's and a clean-looking hunk proves nothing about which of you wrote it. Treat this as the expected form of the claim, not as exceptional diligence.

**Re-check embedded `file:line` citations after your final edit, not during.** An agent writing citations into a file is editing the very thing its citations point into, so every subsequent edit in the same pass shifts lines it has already written — the check has to be the last action of the pass, not a step inside it. Re-grep the identifier rather than re-reading the number; this file's own citations moved by 8–10 lines inside an hour for exactly this reason.

**Better still, prefer a file + identifier citation over a `file:line` one, so there is no number to re-check.** A line citation is a standing dependency on every edit anyone makes above it, in a file you do not own and cannot lock; an identifier citation — a function, a const, a prop, a config key, a payload key — travels with the thing it names and cannot drift. Two exceptions, and they are the whole of the judgement. Keep the line where **there is no identifier to name**: one paragraph of a docblock, an HTML comment, one of several identical tags. And keep it where **the number is itself the claim** — a dated reading of a tree is evidence, not a locator, and renumbering it destroys the measurement it recorded.

Established the hard way, sweeping this directory on 2026-09-06: **five wrong line citations across four distinct claims** (one written twice), and **every one of them already named an identifier in the same sentence**, so every one would have survived with the number simply deleted. `optimisticVisitOptions` cited at `:321` when the declaration is at `:327`; `HomeController.php:83-84` for two payload keys that had moved to `:103-104`, in two sections; `PetCardCommentButton.vue:76-85` for a clamp that lives in `countDeleted()`, `:76-85` being the `defineProps` block; and `PetOwnerActions.vue:15` in `js.md` for an import at `:16`. A stale citation inside `.ai/rules` is worse than the same defect in a component docblock, because these files are the artefact that outlives the session and the one agents are explicitly instructed to trust.

## A written gap is a tripwire; an unwritten one is not
That sentence is the rule. The mechanism is what makes it more than an assertion: a recorded gap gives the next agent something to notice an *interaction* with, and an unrecorded one absorbs a widening in silence.

Worked instance. `.ai/rules/enums.md:21` records that every enum `label()` returns hardcoded English with no `__()`, as a deliberately-open gap owned by a scheduled i18n pass. A correct parity fix then moved those English strings onto the **public feed, for every visitor including guests** — the busiest page in the product — where before they surfaced only on pet-detail and profile pages. Nothing about the fix was wrong; what changed is the blast radius of an accepted defect. The agent making the fix could see that, and could say so, **only because the gap was already written down**. Had it not been, the widening would have been invisible: no diff line says "this known-bad string now reaches ten times the traffic".

So the argument for recording an accepted gap is not "so we remember it". It is that an accepted gap is a claim about *how bad* something currently is, and later work routinely changes that number without touching the thing itself. Write the gap down and the next change collides with it; leave it out and the gap quietly gets worse with nobody learning it did.

## The interval between a finding and its fix is a drift window
A distinct drift mechanism from the one this file already catalogues. Everything else recorded here is **a claim outliving its subject** — a docblock, a cross-file citation, a measurement whose importer moved. This is **a queue outliving its premise**: the finding was true when it was written, the world changed, and the finding sat across the change.

Two worked instances, kept as a pair because they resolve in **opposite directions** and the pair is what teaches the shape.

- *Stale by relocation*: a review nit cited `@/lib/commentSurface`. A *different fix in the same remediation round* moved that file to `resources/js/composables/useMutationSurface.ts`, so by the time the nit was briefed it named a path that no longer existed. The reviewer had verified the path; verification is not the mitigation here, because nothing was wrong at the moment of writing.
- *Stale by consumption*: an unused-import warning for `VisitOptions` at `resources/js/composables/useNotificationInbox.ts:1` was observed real by one agent; unrelated later work made the import **live** — it is now the return type of `optimisticVisitOptions` in that file. **Cited by identifier because the line citation that used to sit here was itself stale**: this bullet said `:321`, and the declaration is at `:327`, re-established 2026-09-06 by grepping the identifier. It was already `:327` before the most recent edit to that file, which was line-neutral — so the defect was staleness inside `.ai/rules`, not drift introduced by the edit, and a rules file is the worst place for it because the rules are what agents are told to trust. Confirmed 2026-09-06 by reading both lines; `npm run check` is clean at **0 warnings across 230 files** — first reported by the agent that ran it, then independently re-run and re-confirmed on 2026-09-06, so the figure no longer rests on a single report (it was not run again in this pass). The finding was true when written and the defect no longer existed when it was briefed. Nothing moved and nothing was renamed — the file absorbed the finding.

The mitigation is that **a queued finding is re-read against the current file and the defect confirmed to still exist before it is briefed, and the brief must explicitly permit changing nothing.** *Confirm it still exists*, not *locate it*: the difference is load-bearing, because only the confirm phrasing has an "it is gone" branch. Name the failure mode, because it is the part that bites: an agent told to locate a defect that no longer exists usually does **not** error. It looks harder rather than concluding absence, then manufactures a plausible edit for the file it is actually looking at — which is indistinguishable from success in a report that says "done".

**The self-referential instance is the strongest one, because this mechanism struck the authoring of this very clause.** The claim that the deletion-check discipline was absent from `.ai/rules` was verified with two independent searches on different terms and reported as established — and it was true when made. Measured since: `git show 2ed96da:.ai/rules/general.md | grep -c "Review what a change REMOVED"` returns **0**, while the section exists in the working tree — at `:93` when that count was taken, and at `:102` after this correction pass grew the sections above it, which is the same drift in miniature. An earlier, still-uncommitted rules pass had added it in the interval between the finding and the fix. The correct handling was to **extend the existing section rather than append a near-duplicate beside it**, which is what kept this file coherent; `.ai/rules/routes.md` records why — a stale justification sitting next to a corrected one is how the correction gets reverted.

This argues *for* carrying findings verbatim with their file paths, not against queuing them. Verbatim text plus a path makes a mismatch surface as a contradiction the agent has to raise; a paraphrase ("tighten up the comment surface helper") is satisfiable against whatever is there now, so it never contradicts anything.

## Name the invariant, not the edit
When you brief a change, state the property that must hold afterwards, not the keystrokes. An edit is satisfiable in ways that break the property; an invariant is not. Three catches this phase, and the pattern is only visible across all three:

1. An instruction to remove something from a **guest** branch was satisfiable by a deletion that would also have broken the **authenticated** branch. The edit was well specified; the property "the signed-in path keeps its control" was the thing that had to survive, and only naming it made the difference visible.
2. "Port legacy's truthiness check" **does not hold on the driver this app runs on.** `pets.weight` is an uncast `decimal` — `DecimalColumn = number | string` in `@/types/profile` — served as a float by SQLite and as a **string** by MySQL, and `Boolean('0.00')` is `true`. So the literal port suppresses the weight tile on the test driver and renders a "0 kg" tile on the dev/production one. `Number(pet.weight) > 0` holds the invariant on both and is the coercion this codebase already applies at every other `DecimalColumn` boundary (the `weight` computed in `resources/js/components/pets/PetQuickInfo.vue`, whose docblock says it was established by reading both trees rather than by rendering either). Worth noting how it was found: `vue-tsc` refused the narrowing, so a **type error was the discovery mechanism for a runtime behaviour difference between two database drivers**.
3. "Pass `replies_count - replies.length`" goes **negative** once a sibling fix adds a local offset. The invariant — *the count reflects what is on screen and never renders below zero* — survives; the subtraction does not.

The resolution in (3) is the worked pattern and is worth keeping: **clamp the offset, not the rendered number.** `resources/js/components/pets/card/PetCardCommentButton.vue` holds `offset` and clamps it at `-commentsCount` inside `countDeleted()` — cited by identifier because the line range that used to sit here, `:76-85`, addressed the component's `defineProps` block on 2026-09-06 and not the clamp, which is in `countDeleted()` — because `commentsCount` is a snapshot from render time while the dialog shows the thread as it is now, so a reader can legitimately delete comments the snapshot never counted. Clamping the display instead would let the offset sink arbitrarily negative, and a later post would be spent climbing out of a number nobody ever saw. `advertisedReplies` in `CommentItem.vue` is the sibling case, floored at one rather than zero because it is only read under `hasMore`.

## Review what a change REMOVED — and what it merely made optional
Two halves of one review check. They are recorded together on purpose: a reader who has just been told to look for deletions is exactly the reader who needs to be told deletions are not the only shape.

**First half — check what a change REMOVED, not only what it added: did anything true die with it, and is it still written down somewhere.** Two independent greps of `.ai/rules` on 2026-09-06 found it nowhere: one for the expected wording (`grep -rinE 'what a change removed|did anything true die|removed, not only what'`), one deliberately broader (`grep -rinE 'removed|deletion|deleted|died|lost'`, domain noise filtered out by hand), plus a read of every `^## ` heading in this file and in `tests.md`. Every hit was about *data* deletion — purging a pet, soft-deleting a conversation — and none about review discipline. The check existed only in orchestrator briefs for two phases, delivered to an agent only when an orchestrator happened to quote it, so any agent working without one never saw it.

Provenance, because it has earned its cost by name twice in the UI port. It caught an **`aria-label` must extend its trigger's visible text** constraint that died with an otherwise-justified deletion — the constraint is re-established and now survives in the docblock of `resources/js/components/messaging/StartConversationButton.vue`, together with the SSR measurement that proves the prop lands. And it caught a surviving fact a deletion nearly took with it: the "there is no presence dot, because **no code path writes `last_seen_at`**" reasoning, now at `resources/js/components/shell/ShellUserMenu.vue:24-30`.

**Read "removed" as covering what a file *recorded*, not only what it rendered.** A deleted component takes its docblock with it: the invariants it pinned, the alternatives it had already rejected, the reason a value is what it is. Markup that disappears shows up in a screenshot and in a diff someone will read. A rationale that disappears shows up nowhere, and the next agent re-derives it wrongly, or not at all, and then argues the settled question again. The recorded half is the half that dies silently, so it is the half to check first.

**Second half — a capability can be lost by WIDENING a contract as well as by deleting code.** A deletion detector structurally cannot see this: nothing is removed, every existing call site still compiles, the type gets *more* permissive rather than less, and the loss manifests only at a call site that never supplied the value. There is no diff line to notice.

**Operationalise it,** because "be alert to it" gives a reader nothing mechanical. On every diff, enumerate **every prop or parameter that gained a `?`, a `nullable`, or a default**, and for each ask **whether every current mount site or caller supplies it**. That is checkable against a diff.

Worked example — measured on the uncommitted working tree of branch `upgrade/laravel-13` at HEAD `2ed96da`, by reading the files and running the greps named here, so it can be re-checked:

- `resources/js/components/comments/CommentItem.vue:46-49` had three props widened in the diff: `maxLength: number` became `maxLength?: number | null`, and `reportCategories` / `reportReasons` each gained a `?`. `CommentsDialog.vue:88-90` declares the same three optional. That widening is what made the comments dialog mountable on a feed card.
- Working case: `resources/js/pages/pets/Show.vue:70-71` declares `reportCategories` and `reportReasons` **required** and supplies them at `:126-127`.
- Broken case: `app/Http/Controllers/Web/HomeController.php` supplies neither — `grep -cE "reportCategories|reportReasons|ReportCategory"` against it returns **0**. The feed chain reads them off page props that are never set: `PetListingCard.vue:101-109` casts `page.props.reportCategories` as `| undefined`, forwards through `PetCardActions.vue:88-89,153-154` and `PetCardCommentButton.vue:50-52,67-69` into `CommentsDialog`, and `CommentItem.vue:111-112` and `:126-127` forward both straight into the report affordance.
- Net: the dialog mounted from a feed card receives `undefined` for both, so that affordance has nothing to render. Nothing errors, types are clean, and the suite on that tree is green.

Those readings are of that tree, not of today's — `HomeController` ships both keys now, as `'reportCategories'` and `'reportReasons'` in the `Inertia::render()` payload of `HomeController::index()`. Cited by key rather than by line **because that line citation has already gone stale once**: it read `:83-84`, and on 2026-09-06 the two keys are at `:103-104` while `:83-84` is the signature of `index()`. Keep the numbers in the bullets above as taken — they are a dated measurement of a tree, not a locator; the resolution is two paragraphs down.

Related tell, same defect wearing a different hat: the `as ... | undefined` cast at `PetListingCard.vue:101-109`. A type assertion that makes a server-supplied prop optional silences the one tool that would otherwise have caught the missing key. Treat a widening cast on page props the same as a `?` in a prop declaration.

**The counter-case, in this section on purpose, because the answer is not "narrow everything".** An optional capability with no current consumer is sometimes correctly **kept**, because the right fix consumes it. `resources/js/components/pets/PetSectionHeading.vue:29-34` declares `level?: 'h2' | 'h3' | 'h4'` defaulting to `h3`; no caller passed it, and a reviewer proposed deleting it as dead surface. The correct fix for a sibling finding was to have `PetQuickInfo` — a standalone section, not nested under the facts card's `h2` — reuse that component rather than carry a second copy of its classes, which it now does at `PetQuickInfo.vue:115-119` with `level="h2"`. Same question, *does anything actually supply or consume this?*, opposite answer: deleting the prop would have removed the capability the very next fix needed. So the enumeration in "Operationalise it" is a prompt, not a verdict — it tells you which declarations to look at, and what the surrounding work is about to do decides whether each one is a regression or an affordance waiting for its caller.

**The two halves of this section failed in opposite ways, and a reader needs the difference.** The first half was **known and never written down** — a delivery failure, and the *third* instance of exactly what "A rule's glob must cover where the mistake gets made" above already documents (the first was `index.md`'s preamble telling agents to read only the first matching file; the second was the comment-subtree rule filed under the glob where the fix lived, not where the mistake gets written). The second half was **never known at all** — a discovery. Only the second is new knowledge. Without that distinction the whole section reads as something the process caught, when half of it the process missed for two phases while the correct check sat in briefs nobody guaranteed an agent would receive.

That this file documents "a rule's glob must cover where the mistake gets made" while a two-phase-old check sat outside the file entirely is both the strongest available argument for that rule and the clearest evidence it does not enforce itself. Recording a rule is a step in the work, not the write-up afterwards.

**Why this lives in one file, and why that file is this one.** Two precedents here pull opposite ways and neither is clean. This file's own standing rule prefers the widest glob whose files could contain the mistake — but it was written against *an enumeration going stale* (three directories, and a fourth flow later got its own), and this defect's surface is not an open-ended set of directories. It is a small, stable set of kinds of declaration: a Vue prop gaining `?`, a PHP parameter gaining a default, a `required` relaxing to `nullable`, a resource key becoming conditional. An enumeration that cannot go stale is not the failure that rule guards against. The other precedent is the deliberate triplication of "A form's read resource and its rules must use identical key names" across `resources.md` / `requests.md` / `concerns.md` with an explicit *"Edit all three together"*. Applied faithfully here that is four or five copies, not three — `js.md`, `app.md`, `requests.md` **and** `concerns.md` (validation rules live in the `PetValidationRules` trait, not in the requests), and `resources.md`. Five copies of a paragraph drift, and a rule about claims drifting apart, living in five drifting copies, would be the worst outcome on the table.

The trade-off stated plainly: **the widest glob maximises nominal reach and may minimise actual reading; triplication maximises reading and minimises durability.** The tie-breaker is *when* each rule is needed. Key-parity is an **edit-time trap** — it bites the person typing in one particular file, so it has to be in front of that person, which is what earns it three copies. This is a **review-time check** run over a whole diff, and the person who needs it is holding a change set rather than a file. No per-directory glob matches "the change I am about to close out"; `**` always does. That is a positive reason for this file, not a default.

The scroll-past problem the key-parity rule was not trusted to survive is real, and it is answered by **pointer, not copy**: `js.md`, `app.md`, `requests.md`, `concerns.md` and `resources.md` each carry a one-line cross-reference to this section. A pointer carries a file name, not a claim, so it cannot fall out of step with what it points at — which is exactly the property five copies would lack. If a pointer ever goes stale it goes stale loudly, because the section it names is either there or it is not.

**Third check, same family — what did your change make FALSE?** The removal check asks what your change destroyed; this asks what it falsified. A change that is entirely correct in itself routinely leaves a true sentence elsewhere untrue: a docblock describing the behaviour you just replaced, a rule quoting a number you just moved, a comment naming a prop you just renamed. Nothing fails, and the sentence keeps being read.

The boundary between fixing that and reporting it is the **causal link, not proximity**: **correct a claim your own change makes false or makes worse; a false claim you merely notice in passing is a finding to report, not a fix to make.** The line is drawn there because it is the only one an agent can actually apply. *Did my edit make this wrong?* is answerable from the diff in front of you. *Is this close enough to be mine?* is not answerable at all, so in practice it resolves to whatever the agent felt like doing, in both directions — a lane violation on one run and an untouched contradiction on the next.

Read it as a **completeness requirement on the change you were already sent to make**, not as an exception to scope discipline. Nothing here widens a task: the claim your change falsified is part of your change in exactly the way the thing your change removed is.

**The two are not always separable, and the clause matters more than the boundary.** If your correction leaves an **uncorrected sibling** that now contradicts the tree, that sibling is yours to **report as urgent** even though you did not write it and must not edit it. You did not make it wrong — you made it *contradictory*, which is a different and worse defect. Worked case, this phase, **reported by the agent that hit it rather than re-observed here**: two header docblocks were correctly rewritten and cited `resources/js/components/messaging/MessagesDropdown.vue:131` and `:139-143` as their evidence, which turned an ordinary stale sentence at `MessagesDropdown.vue:26-29` into a direct contradiction of two freshly-corrected files that name its own file by line. Stale before, contradicted after — and the second is the worse of the two, for the reason in the next paragraph.

Re-read on 2026-09-06 while recording this, and the re-read is part of the lesson: `:131` is `const canRead = computed(() => viewer.value?.email_verified_at != null);`, `:139-143` is the `onMounted` that calls `ensureLoaded()` under it, and the docblock at `:26-29` now **agrees** with both. So either the sibling was corrected in the interval or the citation has moved, and this pass could not tell which from the tree alone. Keep the case — the mechanism is what earns its place, and it does not depend on the instance still being live — but read the line numbers as the reporter's, taken on a tree several agents were writing to. This is the drift window above in miniature, arriving while a rule about it was being written.

**A partial correction can leave the tree worse than no correction — which is why the clause above is urgent rather than tidy-up.** A lone false comment is a defect a reader may simply believe: bad, but it fails in one direction and a later reader can still disprove it. A false comment **contradicted by a corrected sibling** forces the reader to adjudicate, and readers do not adjudicate neutrally — they resolve toward the file they are editing, which is the uncorrected one. The half-done correction can therefore hand the wrong claim *more* authority than the whole-done nothing would have.

The remedy is not to correct less. It is to **enumerate every instance of a claim before correcting any of them** — grep the claim, not the file — and to treat "found in three files, fixed one" as **unfinished, not scoped**. This is the search-completeness discipline of "Establish runtime behaviour by running it, not by reading the source" above, pointed at a *write* instead of at a read; the write side is the worse of the two, because a missed instance in a read costs you a wrong belief while a missed instance in a write costs every later reader theirs. Where you genuinely cannot fix them all — the remaining copies are another agent's files — the enumeration itself is the deliverable: report every instance by path and line, as the urgent item above, rather than reporting the one you fixed.

## record-rule appends and never merges: create with it, merge with Edit, then verify
Two structural limits of the Boost `record-rule` MCP tool, and the authoring sequence they force. Both were first read out of `vendor/laravel/boost/src/Rules/RuleRepository.php` and then **re-established by running `RuleRepository` against a scratch directory** — per "Establish runtime behaviour by running it" above, reading the source only tells you what it should do.

**Limit 1 — `record-rule` appends; it does not merge.** `appendEntry()` (`RuleRepository.php:307-312`) does `File::put($contents."\n\n## ".$title."\n".$note."\n")` unconditionally, and `write()` calls it on every path (`:130`). Nothing anywhere looks for an existing heading. Passing an **existing heading verbatim therefore produces a second, identical `## heading` at the end of the file** — and the call returns the file path and reports success. Ran it: two `write('app/Models/**', 'Alpha rule', …)` calls into a scratch directory left a single `models.md` containing `## Alpha rule` twice, one entry under each.

That is the worst failure this particular tool could have. "Extend the existing section rather than append a near-duplicate" is standing guidance here — see "The interval between a finding and its fix is a drift window" above, and `.ai/rules/routes.md` on why a stale justification sitting beside a corrected one is how a correction gets reverted. An agent following that guidance reaches for `record-rule` with the existing heading, receives success, reports success, and leaves a duplicate heading behind in the file whose entire subject is claims drifting apart from each other. Green report, silent failure, and the damage is exactly the thing the guidance existed to prevent.

**Limit 2 — `areaKey()` collapses every dotted root-level glob to the empty area.** `meaningfulSegments()` (`:257-264`) drops any path segment containing `*` **or `.`**, and `areaKey()` (`:249-252`) joins whatever survives. A root-level filename is a single dotted segment with no directory in front of it, so nothing survives and the area is `''` — the same area as `**`. Measured by running `areaKey()` through reflection: `**`, `**/*.php`, `composer.json`, `composer.lock`, `vite.config.ts` and `phpstan.neon` all return `''`; `config/media-library.php` returns `config`; and `.ai/rules/**` returns `rules`, because `.ai` is dotted and disappears too.

The consequence, also run rather than reasoned: `resolveTargetFile()` (`:184-191`) returns the **first** rule file holding any path in the same area, so once one file carries `**` every later dotted root-level glob lands in that file whatever the author intended. In the scratch run, `vite.config.ts`, `phpstan.neon` and `composer.json` all appended to `general.md` and silently grew its frontmatter. An empty rules directory is no better: `uniqueFilePath()` falls through to the literal `'general'` candidate (`:226-228`) because there are no meaningful segments left to slug, so a first-ever rule for `composer.json` still creates `general.md`. In this repo `general.md` is the file that carries `**`, and the only rule files sorting ahead of it are `actions.md`, `app.md`, `comments.md`, `concerns.md`, `config.md`, `controllers.md`, `data.md`, `enums.md` and `factories.md` — none of which holds an empty-area path. So today every dotted root-level glob resolves to `general.md`. `.ai/rules/vite.md` has `paths: [vite.config.ts]` and `record-rule` demonstrably cannot have produced it (it was created some other way, by hand or by a later frontmatter edit); a `record-rule` call with that glob today appends to `general.md` instead, because the empty-area match on `general.md` is tested before `vite.md`'s exact-glob match is ever reached. If a dotted root-level file needs its own rule file, create the file and its frontmatter with `Write`/`Edit` and keep `record-rule` out of it.

**The sequence these force is three steps, not one.**

1. **`record-rule` to create a new section.** Creating is the only operation it performs correctly.
2. **`Edit` to merge into a section that already exists.** Never `record-rule` with an existing heading — see Limit 1. The same goes for frontmatter: growing an existing file's `paths` is an `Edit`.
3. **Verify afterwards, by inspection.** No rule file contains a duplicate `## ` heading, and `index.md` still maps every rule file. The shape is `grep -c '^## '` per file plus a duplicate-heading sweep over the directory — `for f in .ai/rules/*.md; do grep '^## ' "$f" | sort | uniq -d | sed "s|^|$f: |"; done`, where silence is the pass — and `comm -13` between the rule files on disk and the paths named in `index.md`.

**An agent that stops at step 1 has not finished the job.** Step 3 is required *regardless of whether you believe you had the directory to yourself*, because verification is also the only thing that catches a concurrent writer. Do not assume exclusivity: seven rule files were rewritten during one agent's read phase by a different agent finishing a pointer pass, under an explicit guarantee of exclusivity that was simply unenforceable. Reported by the orchestrator rather than observed here, but corroborated by mtimes on 2026-09-06 — `js.md` 15:15:14, `lang.md` 15:15:26, `requests.md` 15:15:56, `concerns.md` 15:16:03, `resources.md` 15:16:13, `app.md` 15:16:18, `enums.md` 15:16:29: seven files inside 75 seconds, 5–12 seconds apart. Nothing collided that time. The mechanism that would make it collide is in the source: `appendEntry()` is an unlocked read-modify-write (`File::get` at `:309`, `File::put` at `:311`), and `writeIndex()` (`:137-161`) regenerates `index.md` wholesale on every call, so a concurrent append or a hand-edit to the index landing in the wrong half of that window is dropped with no error. That last part is established by reading the source, not by racing it — treat it as the shape of the risk, not as a measured failure rate.

## Amplification toward inaction: absence of a tool is evidence about the tool, not about the task
Three things in one section, because they are one episode: a false claim about what this fleet **cannot** do, the method that disproved it, and the environment trap that made attempting it look broken.

**The chain, with both hops attributed, because it survived a written provenance discipline built to catch exactly this.**

1. *There is no `playwright`, `vitest` or `jsdom` in `package.json`* — **true, and checked.** Re-checked 2026-09-06 on this working tree: `grep -nE 'playwright|vitest|jsdom|puppeteer|cypress|happy-dom' package.json` exits 1 with no output, and `devDependencies` holds nine entries (`@laravel/vite-plugin-wayfinder`, `@tailwindcss/vite`, `@types/node`, `@vitejs/plugin-vue`, `concurrently`, `typescript`, `vite`, `vite-plus`, `vue-tsc`), none of them a test runner or a DOM shim.
2. → *therefore this fleet cannot observe rendered behaviour* — **an inference, stated as a property of the fleet.** The coordinator offered a dichotomy: add a dependency (needs owner approval) or record a permanent named gap. That framing silently excluded the third option — drive what is already installed.
3. → *brief agents to write "reasoned, not observed, and not observable by this fleet", and treat the gap as permanent* — **a prohibition**, hardened into standing brief language by the orchestrator, which then **suppressed the attempt for several rounds**. It was disproved only when an agent ignored the framing and tried.

Both parties are named on purpose: the false dichotomy at hop 2 and the hardening at hop 3 are separate contributions, and the interesting fact is that the pair passed a discipline explicitly designed to catch a claim getting more confident as it travels. Note also which correct rule was about to be applied to the wrong object: "A written gap is a tripwire; an unwritten one is not" (above) would have had the fleet record the gap in good faith. Recording a gap does not make the gap real.

**Why this earns its own entry: the absence of an attempt leaves no artefact to review.** Every other failure catalogued in this file ends in a *thing* — a wrong comment, an inert prop, a stale citation, a manufactured edit — and a reviewer holding a diff can find it. This one ends in nothing. **"Unattempted" and "impossible" are indistinguishable in a report that says neither was tried.** The direction is the point: the drift recorded elsewhere here licenses **doing something wrong**; this licensed **not doing something right**, and only the first kind leaves evidence behind.

**The tell is mechanical, so use it as one: a claim about what *cannot* be done, grounded in what is *absent*. Absence of a tool is evidence about the tool, not about the task.** When a brief is about to say "not observable", the obligation is one attempt with what is installed, and the report says which attempt was made.

**The method, recorded so nobody re-derives it. Browser verification needs no new dependency and touches no repo file.**

1. `rsync` the working tree to an isolated copy **outside the repo**.
2. Symlink `vendor` and `node_modules` into the copy.
3. **Remove `public/hot` in the copy** — see the trap below; skipping this step is what costs the debugging cycle.
4. `npm run build` **in the copy, never against the working tree** — a build against the tree rewrites shared, gitignored `public/build/` underneath whatever else is running, which is the same concurrent-writer hazard "Run Pint with explicit paths" records.
5. Serve the copy with `php artisan serve` against a **throwaway sqlite database**, with explicit `DB_CONNECTION=`/`DB_DATABASE=` shell overrides rather than an `--env` flag (`.ai/rules/migrations.md` records why the flag is the wrong instrument for anything destructive).
6. Drive Chrome over CDP.

Net effect: no dependency added, no repo file changed, only gitignored `public/build/` regenerated inside the copy.

- **Synthetic input did not reach the page** in that build. Controls were driven instead by **in-page `PointerEvent`/`click` dispatch** on the target element.
- **reka-ui `Select`s could not be driven that way at all** (`reka-ui ^2.9.8`, `package.json:25`, wrapped under `resources/js/components/ui/select/`). Form values were set on the **hidden native `<select>` element the reka Select renders and that `<Form>` (`@inertiajs/vue3 ^3.0.0`) serialises** — set `.value` there, dispatch `change`, submit.

Write that line, not a softer one: "we cannot really check the rendering" and "we cannot check announcement" are a whole class apart, and every softening of the first has been read as licence to stop trying, which is the failure this section exists to document. The hedge that belongs here is the one recorded above — these are observations from one Chrome build on one machine — and it attaches to *how reliably the instruments drive*, not to *whether the property is observable*.

**Correction to a recorded instrument claim, and the general form is the part that lasts.** This repo records that `getComputedStyle` "cannot see" a clipped `box-shadow` and reads the same value either way — `resources/js/components/pets/card/PetCardHeader.vue:14-22`, where a clipped focus ring was settled by sampling painted pixels instead. The accurate reason, which survives both cases and the next one: **an overlap is a relation between two rendered boxes, and no single element's computed style expresses a relation.** Computed style tells you what one box was asked for; only positions — `getBoundingClientRect()` on *both* boxes, or the painted pixels — tell you where the two ended up with respect to each other. So the trigger is the shape of the claim, not the property being inspected: whenever a claim reads "A covers / clears / collides with / sits inside B", reach for a two-box measurement. The docblock at `PetCardHeader.vue:14-22` still carries the narrower premise; it is in `resources/js/**` and belongs to that owner, so it is reported here rather than edited.

Read every line number in this section as a reading taken **2026-09-06 on a working tree with other agents writing to it**, not as a stable address — three of the citations above moved by 8–10 lines between the first draft of this section and its verification pass an hour later, which is the drift window in miniature. Re-grep the identifier, do not trust the number.

**The `public/hot` trap, stated separately because the symptom does not suggest the cause.** A stale `public/hot` makes Laravel's Vite helper serve every asset from the URL inside that file instead of from `public/build/`. When the URL belongs to **another project's dev server** on the same port, the page loads and then fails in ways that do not resemble a stale-asset problem — wrong or missing modules, not a manifest error — and it cost an agent a full debugging cycle. Nothing removes the file when a dev server stops: on this tree, 2026-09-06, `public/hot` is 21 bytes containing `http://127.0.0.1:5173`, last written 2026-09-03. Removing it in the copy is a required step of the recipe above, not an optimisation.

**Why all three live here, in one section, and not in `js.md`.** The three parts split on the review-time/edit-time axis this file already uses to place rules — the boundary statement and the computed-style correction added later belong to the first part, being what the chain got wrong and how it was disproved, not a fourth thing. The chain is **review-time**: it bites an orchestrator writing a brief or a reviewer deciding whether a claim is checkable, and neither is holding a file, so no per-directory glob delivers it and `**` always does — the same argument that put "Review what a change REMOVED" here. The `public/hot` trap is **run-time for whoever runs the app**, which is not only the frontend agent: a backend agent serving the app to look at a controller's page hits the identical symptom, so `resources/js/**` would under-deliver it. The recipe is **both**, and that is precisely why splitting fails: filed in `js.md` it would be invisible to the reviewer who needs it as the answer to "can this be observed?", and filed here alone it would be one pointer away from the frontend agent who needs it to look at a render. Separating the disproof from the failure it disproves would leave each half weaker — the recipe without the chain reads as trivia, and the chain without the recipe reads as an unfixable complaint. Per the pointer-not-copy precedent above, `js.md` and `tests.md` carry a one-line cross-reference to this section rather than a copy of it.

## Two workstreams on the same lines get a third owner, not a priority order
When two workstreams need to change the same lines, do not resolve it by ranking them. Give the shared surface a **third owner** — one task neither workstream runs, whose output both inherit as input.

The argument is mechanical rather than stylistic, which is why "just tell them who goes first" keeps not working. **A priority order between peers is only executable if each peer knows the other's state**: "B waits for A" requires B to observe whether A has finished, and that is exactly the information neither of them has about the other. What the pair actually does is either both wait — the deadlock shape — or both write, which is the concurrent-writer hazard "record-rule appends and never merges" records above, where `appendEntry()` is an unlocked read-modify-write (`RuleRepository.php:307-312`) and the loser's write vanishes with no error. **Ownership requires no shared state; precedence does.**

Worked case this phase, reported by the coordinator rather than observed here: two review gates both required the same two header docblocks rewritten, and neither could proceed on a file the other might be mid-edit on. A single shared-surface task, owned by neither gate and run once, produced the rewrite; both gates then read it as input and closed against it. Cost: one extra task. What it bought: no ordering assumption anywhere, and no version of those files that only one gate had seen.

Two consequences worth stating, because the shape recurs. The third owner must be given the *union* of what both workstreams need from those lines, or it ships a rewrite one gate then has to redo — which reintroduces the shared surface it was created to remove. And `.ai/rules/general.md` is itself a shared surface by construction: every `**` glob resolves to it (see the `areaKey()` limit in "record-rule appends and never merges" above), so a phase where several agents have rules to record into it wants **one recorder holding the whole set**, not a queue of appenders.

## A citation proves a claim has a subject, not that the claim is true of it
Read the primary text before acting on any characterisation of it. A `file:line` attached to a finding is evidence that the finding **has a subject**; it is not evidence that the finding is **true of that subject**. The citation is what lends it the look of having been verified, so it passes review by inheritance — a reviewer confirms the line exists, finds it does, and never re-reads the sentence.

This is **not** the drift window recorded above under "The interval between a finding and its fix is a drift window", and filing it as one loses the mitigation. That is a finding that *was* true and went stale because the world moved. This is a finding that was **never accurate about its subject**, so nothing has changed and re-reading for staleness structurally cannot catch it. Drift wants "re-confirm the defect still exists before briefing". This wants "**read the primary text, not anybody's summary of it**".

**Worked specimen — the chain is what teaches it, so keep all five links.**

1. `resources/js/components/pets/card/PetCardHeader.vue:14-22` states, correctly for its own case, that computed style reads the same `box-shadow` whether or not an ancestor's `overflow: hidden` clips it. **True**: what differs is the ancestor's clip box, not the element's own property.
2. That true narrow claim was **generalised into a false wide one** — that computed style cannot distinguish the RTL padding arrangements. **False**: `pr-6` versus `pe-6` under `dir="rtl"` produce `padding-right: 24px` versus `padding-left: 24px`, which computed style distinguishes perfectly well.
3. A review correctly caught the **wide** version.
4. The correction was then aimed **back at the true narrow original**, as though it were the defect — which would have replaced a correct statement with a wrong one.
5. It was stopped only by someone **opening the file and reading the actual sentence**, rather than the finding's characterisation of it.

The failure is at step 4, and it is a correction introducing a new wrongness. **That is the third distinct mechanism by which a correction has done that this session**, and the three are not interchangeable: a partial correction leaving a contradicting sibling ("Review what a change REMOVED — and what it merely made optional"); a queued finding whose defect had already gone ("The interval between a finding and its fix is a drift window"); and this one. ## A claim that is true only within a scope must state the scope
The companion to "A citation proves a claim has a subject, not that the claim is true of it" above, and the reason that specimen's narrow claim got mis-generalised in the first place: **it never said why it was narrow.**

`resources/js/components/pets/card/PetCardHeader.vue:14-22` says computed style "reads the same 3px shadow either way" — true, and it hands over the observation without the boundary. One subordinate clause would have stopped the over-generalisation dead: the identity of computed style holds *there* **because the differing property belongs to the ancestor's clip box, not to the element itself**. With that clause present, carrying the claim across to `pr-6` versus `pe-6` is visibly out of scope, because `padding-right` is the element's own property and the clause does not cover it.

General form: **a claim that is true only within a scope should state the scope, or it will be applied outside it.** A reader holding only the observation has no way to tell a narrow truth from a wide one, and the wide reading is the more useful-sounding of the two, so the wide reading is the one that travels. The cost of prevention is a clause; the cost of omission is the five-link chain in the section above, which ended one step short of replacing a correct sentence with a wrong one.

This sharpens rather than replaces the standing obligation under "A claim must say how it was established" that every number names the pair it was measured against. That one is about *how* a claim was established; this one is about *where* it holds. A claim can state its method exactly and still be silent on its boundary, and the silence is what gets it re-used somewhere it is false.
