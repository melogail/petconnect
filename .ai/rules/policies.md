# Policies

> **`.ai/rules/app.md` also applies to this path and must be read too.** Its `app/**` glob
> covers everything covered here; this file adds to it rather than replacing it. Do not stop at
> the first row of the index that matches — the index is regenerated by `record-rule` on every
> write, so its ordering and wording carry no meaning.

## A policy method a Resource asks per row must not query
MessageResource emits `can_edit`/`can_delete` by calling `$viewer->can('update'|'delete', $message)` for every message on a page, so MessagePolicy::update and ::delete decide only from attributes already on the model (sender_id, created_at, a config window) and load no relation. A participation check in either would be one query per rendered row — thirty on a thread page — and nothing would catch it: Gate calls are invisible to `preventLazyLoading` reasoning and the resource looks free.

MessagePolicy::create and ::pin are the opposite case: asked once per request against a route-bound model, so they may (and do) call Conversation::hasParticipant() — and ::create also Conversation::acceptsMessagesFrom(), the recipient-side consent question. ConversationPolicy::view is the same shape.

Rule: before a resource asks a policy per row, check that the policy method is query-free, and say so in the policy's docblock so the next edit does not quietly add a `whereHas`. If the check needs a query, decide it once for the whole page instead — the thread page decides pinning once rather than per message for exactly this reason.

## A policy's User type hint is a tripwire, not a gate — the guard is what keeps an Admin out
Eight docblocks in this codebase said "Laravel's gate refuses a policy method whose first parameter does not accept the acting user". It does not. `Gate::canBeCalledWithUser()` short-circuits to `true` for any non-null user and only reads the signature to decide *guest* access, so `$policy->update($admin, $review)` is called and PHP throws a TypeError.

The security conclusion still holds — an Admin can never be *authorised* by `App\Policies\**` — but the failure mode is a 500, not a 403, and the thing actually keeping the two apart is `config('nova.guard') = admin`. Do not write the type hint up as the mechanism.

Same correction on closure abilities, where it is worse: `Gate::callAuthCallback()` does `$callback($user, ...)` with no inspection at all. `NovaServiceProvider::gate()` was `fn (Admin $admin) => true`; measured with `nova.guard` nulled, a member got `TypeError: Argument #1 ($admin) must be of type App\Models\Admin` — a 500 out of the belt-and-braces defence. It is now `fn (mixed $user): bool => $user instanceof Admin`, which also gets guests right (an untyped first parameter is what offers the ability to guests, and `null instanceof Admin` is false).
